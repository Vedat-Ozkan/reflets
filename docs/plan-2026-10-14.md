# Reflets: analysis of the plan, feasibility, specs and test strategy

Status: DRAFT, being filled while the deep-research workflow runs. Sections marked PENDING wait on it.

## Context

The owner's notes (`/home/kema/projects/reflets/notes.md`, identical to `sheet-music-plugin/docs/companion-notes-2026-10-14.md`) describe a second product, Reflets: a free, open-source, locally run composing companion for MuseScore Studio 4. Nothing is built. The owner asked for: an analysis of the notes, specs, a feasibility verdict, a study of the existing MuseScore MCP servers (as sources of pitfalls, not as models), a protocol that keeps every link cheap, as much MuseScore plugin-API fact as can be found, and a way for the agent to verify its own work end to end with no unit tests.

Decisions taken with the owner on 2026-10-14, before research:

- Own plugin and own wire protocol, written from scratch. mcp-score and ghchen99 are studied only for the plugin-API pitfalls they hit.
- Efficiency targets both links: the chat-AI-facing MCP link (tokens the model sees) and the server-to-plugin link (latency, reliability, no full re-reads).
- First release slice: read the open score reliably, run rule-based checks (critic), write a proposed idea into MuseScore for audition and approve or discard. Teacher, assistant and collaborator prompts come after, but the core must be designed so they bolt on.
- Two separate apps, like Claude in Chrome: MuseScore on one side, the user's harness (Claude Code first; Claude Desktop, Codex CLI, ChatGPT desktop if possible) on the other. No UI built inside MuseScore beyond the bridge plugin's minimal window.
- Server language is open: Python (imports the engine directly) or TypeScript (spawns the Python engine). Research decides.
- Testing: Claude Code is the test driver. MuseScore exists on the Windows host; installing it in WSL for automated runs is acceptable, but the owner must be able to run flows by hand on Windows too.

## What exists today (read from the sheet-music-plugin code)

Engine facts that shape Reflets (paths relative to `/home/kema/projects/sheet-music-plugin`):

- `engine/score.py`: `ScoreIndex` is built from Verovio's MEI of a MusicXML file, or from `ScoreIndex.from_measures(...)`. Events carry spelled pitch (C# vs Db preserved), staff, layer (voice), onset, duration, grace, tie. Only the first key signature is kept. Standard library only.
- `engine/notes.py`: the N1 compact text form, round-trips through `encode`/`decode` (`tests/test_notes.py`). Keeps spelling, voices, ties, grace notes, chords, bar lengths, meter changes. Drops rests on decode, part identity, clefs, key changes, dynamics, articulations, lyrics, chord symbols, tuplet markup (durations only). ~10x smaller than MusicXML. This is the natural starting point for the model-facing score encoding; it needs rests, part identity and a few marks added for the companion.
- `engine/part_writing.py`: ten voice-leading rules, returns `Finding(bars, beats, voices, rule, why)`. Needs music21 (lazy import). Gated by `applies()` to 2–4 voice chorale textures.
- `engine/harmony.py`, `engine/draft.py` (AnalysisGNN, separate 1.2 GB venv, optional), `engine/check_analysis.py`, `engine/annotate.py` + `engine/render.py` (Verovio engraving, needs MusicXML bytes), `engine/export.py`.
- Without music21 the engine can index, encode N1, build the note table, use harmony, engrave, render and export. music21 (114 MB) is needed for part-writing checks, check-analysis, piano reduction, figured bass.
- Tests are end to end on real files, no mocks of the engine; one golden PNG compared by mean pixel difference; planted-error MusicXML files for part writing (`tests/data/part_writing_*.musicxml`). This is the testing style to carry over.
- `docs/check-analysis-inputs.md`: MuseScore Studio 4.7.5 exports Roman numerals as `<harmony><numeral>` and loses inversions and applied chords. Relevant if Reflets ever reads analysis text from the score.
- Python >= 3.11 in `pyproject.toml`; the venv is 383 MB (music21 114 MB, verovio 29 MB).

## Research findings

### Encoding size, measured locally (Chopin Op. 9 No. 2, 38 bars, 1,253 notes)

| Encoding | Characters | Rough tokens (chars/3.5) |
|---|---|---|
| MusicXML, uncompressed | 509,478 | ~145k |
| MEI (Verovio) | 261,712 | ~75k |
| JSON per note, verbose keys (what ghchen99-style servers send) | 147,685 | ~42k |
| JSON per note, minified, short keys | 58,745 | ~17k |
| N1 note list (`engine/notes.py`) | 5,796 | ~1.7k |

N1 is about 10x smaller than minified JSON-per-note and 25x smaller than verbose JSON. Real Claude token counts still need measuring with the token-count API during implementation; the ratio will hold within a factor of two.

### Deep-research workflow (run wf_c6686bb5-dc7; 24 sources, 119 claims, 25 verified by 3-vote, 19 confirmed, 6 refuted)

Confirmed, high confidence:

- **WebSocket API.** `api.websocketserver` (listen(port, onNewConnected), onMessage(id, cb), send(id, text)) and `api.websocket` client exist from MuseScore 4.4.2 (commit 272077b, Sept 2024) through 4.7.5 (released 2026-09-08) with an identical surface. Text frames only, no close/stop, no disconnect callback, binds all interfaces, clients get integer ids from 2001. Compile-time option, ON in official builds; some distro builds (Arch) omit it. Since 2026-05-07 it lives in the musescore/muse_framework submodule.
- **GUI only.** On 4.7 the console/`--extension` context has no NetworkModule, so the WebSocket API is undefined there. The bridge can only be tested against a real GUI MuseScore. Plugin console.log output is discarded.
- **Undo rename.** 4.7 needs `cmd("action://notation/undo")`; plain `undo` silently no-ops. Unknown action strings are silent no-ops in general, so every write must be verified by read-back.
- **Ties.** No API to create a Tie; `newElement(TIE)+cursor.add` crashes 4.6.5; the only path is `cmd("tie")` over a selection, which toggles.
- **Cursor staff drift.** `INPUT_STATE_SYNC_WITH_SCORE` plus `staffIdx` intermittently writes to the wrong staff; use `INPUT_STATE_INDEPENDENT` with explicit `track`.
- **Plugin cache.** MuseScore caches plugin QML at startup; any plugin change needs a MuseScore restart. A stale instance keeps the port.
- **Qt 6 from 4.4.** Plugins not written for Qt 6 / QtQuick.Controls 2 are silently not listed.
- **Token overhead.** Anthropic's own numbers: 58 MCP tools ≈ 55k tokens; tool search cuts a 50-tool set from 77k to 8.7k. Claude Code defers all MCP tool schemas behind tool search by default; `_meta["anthropic/alwaysLoad"]` (2.1.285+) keeps a tool resident; descriptions cut at 4,096 chars upfront / 16,384 deferred; MCP results warn at 10k tokens and cap at 25k (`MAX_MCP_OUTPUT_TOKENS`); results over 50k chars go to a file. Guidance: fewer than 10 compact tools, 3–5 always loaded.
- **ABC density.** ABC is ~38% of the token length of MIDI-event tokenizations (ChatMusician, ACL 2024); the corpus is monophonic folk tunes, so only the direction transfers.
- **mcp-score's e2e rig** (the strongest template): downloads the AppImage, `--appimage-extract`, Xvfb :87, seeds prefs + shortcuts.xml (Ctrl+Shift+F12) + plugin registration (muse:// for 4.4, musescore:// for 4.5+), launches the GUI with a fixture score, fires the shortcut with xdotool, polls ws://localhost:8765 with `{"command":"ping"}` every 2 s for 60 s, 2 launch attempts; matrix 4.4.4 / 4.6.2 / 4.7.5 on Linux. MuseScore CLI export on Linux also needs Xvfb (`xvfb-run mscore -o`), not `QT_QPA_PLATFORM=offscreen`.

Refuted (0-3): a `scoreStateChanged` change signal usable in MuseScore 4; the specific 14x/6x savings numbers from ghchen99 PR #10 (unverifiable, not the direction).

### MuseScore 4.7.5 plugin API, read from source at tag v4.7.5 (local agent, files cached in the scratchpad `api475/`)

What a legacy v1 QML plugin gets as `api.*`: **only** `api.log`, `api.engraving` (same members as the `MuseScore {}` root), `api.websocket`, `api.websocketserver`. No `api.process`, `api.filesystem`, `api.dispatcher`, `api.interactive` for v1 plugins; v2 extensions (manifest.json) add interactive/theme/converter but deliberately omit process and filesystem.

Reading (all confirmed in `elements.h`): Note `pitch`, `tpc`, `tpc1`, `tpc2`, `accidental`, `accidentalType`, `dots`, `tieBack`, `tieForward`, `firstTiedNote`, `lastTiedNote`, `noteType` (grace), `playEvents`, `userVelocity`; Chord `notes`, `graceNotes`, `graceNotesBefore/After`, `articulations`, `stemDirection`; DurationElement `duration`, `globalDuration`, `actualDuration`, `tuplet`; Tuplet `actualNotes`, `normalNotes`, `elements`; ChordRest `lyrics`, `beamMode`; Segment `annotations` (dynamics, harmony, staff text, tempo as generic items with `text`, `dynamicType`, `harmonyType`, `velocity`), `tick`, `elementAt(track)`; Measure `no`, `tick`, `ticks`, `timesigActual`, `timesigNominal`, repeat flags; Staff `clefType(frac)`, `key(frac)`, `timeSig(frac)`, `transpose(frac)`, `part`; Part `startTrack`, `endTrack`, `instrumentId`, `longName`, `shortName`, `instruments`; Instrument channels with `mute`, `volume` (writable). Spanners (slur, hairpin, tie) via `score.spanners`, `startElement`, `endElement`, `spannerTick(s)`. `score.selection` with `elements`, `isRange`, `startSegment`, `endSegment`, `startStaff`, `endStaff`.

Writing: `score.startCmd(name)` / `endCmd(rollback)` lock the undo stack so everything, including `cmd()`, becomes one undo step, and `endCmd(true)` rolls back. Cursor: `rewindToTick`, `track`/`staffIdx`/`voice` setters, `setDuration(z,n)`, `addNote(pitch, addToChord)`, `addRest()`, `addTuplet(ratio, duration)`, `add(element)` with a documented dispatch table (KeySig, TimeSig, articulations, lyrics, fingering, clef; default path `undoAddElement` covers Harmony, Dynamic, StaffText, Tempo). Note `tpc1`/`tpc2`/`pitch`/`accidentalType` are writable, so spelling can be fixed after `addNote`. `appendMeasures`, `appendPart(id)`, `removeParts`, `removeStaves`, `appendStaff`, `setPartVisible`, `setVoiceVisible`, `setMetaTag`. `selection.select(e)`, `selectRange(startTick, endTick, startStaff, endStaff)` (inside an active command it is applied by tick, deferred).

Files and scores: `readScore(path)` opens a file as a real project in a new tab (only interactive mode; `noninteractive=true` returns null). `writeScore(score, path, ext)` exports the **current** score only, through the export scenario, for any registered writer: musicxml, xml, mxl, mid, mei, pdf, png, svg, mscz, mscx, wav, mp3, flac, ogg, brf. `newScore` is half-implemented (never opens a project) and unusable. `scores` is always empty. `FileIO` can read any path and write under Documents/MuseScore4, temp, plugins, scores, templates, styles. A declarative `QProcess {}` item is registered and can run external programs (`startWithArgs`), although `newQProcess()` returns null.

Hard "cannot do": no change or selection events (`scoreStateChanged` declared but never emitted anywhere in the repo); no list of open scores; no silent file open; no write/close of a non-current score; no insert/remove measures through the API (append only; `cmd("insert-measures…")` unverified); no arguments to `cmd()`; no playback state or transport API beyond dispatching an action code; no plugin run from the CLI (`--extension <uri>` plus `-o` exists for conversion jobs only).

CLI at 4.7.5: `-o`, `-j`, `--score-meta`, `--score-parts`, `--score-media`, `--score-elements`, `-P`, `-F`, `-S`, `-M`, `-r`, `-T`, `--transpose`, `--extension`, `--diagnostic-*`; no `-p`/`--run-plugin`.

Plugin discovery: `~/Documents/MuseScore4/Plugins` (setting `application/paths/myPlugins`), `*.qml` scanned recursively; manifest is a line scan of the `MuseScore {` block (`title`, `description`, `pluginType`, `categoryCode`, `thumbnailName`, `requiresScore`, `version`); `dockArea` and `menuPath` are ignored. `Component.onCompleted` fires before `onRun`. `pluginType: "dialog"` opens through the interactive layer; `quit()` closes it.

### Hosts, SDKs, licensing (local agent, primary sources fetched 2026-10-14)

- **ChatGPT.** Two different surfaces. The ChatGPT chat product (web and the chat side of the desktop app) connects only to remote MCP servers or a Secure MCP Tunnel (an API-key, org-role Platform feature); write actions are Business/Enterprise/Edu only, Pro is read/fetch. The Codex runtime embedded in the ChatGPT desktop app, Codex CLI and the IDE extension does support local stdio servers with write tools, sharing `~/.codex/config.toml` ("Settings > MCP servers"). Codex is included in every ChatGPT plan including Free, or works with an API key, so no separate Codex plan is needed.
- **Codex config.** `[mcp_servers.<name>]` with `command`, `args`, `env`, `cwd`, `startup_timeout_sec` (default 10), `tool_timeout_sec` (default 60), `enabled_tools`, `disabled_tools`, `default_tools_approval_mode` (`auto|prompt|writes|approve`), per-tool `approval_mode` and `output_token_limit`; `codex mcp add <name> -- <command>`. The 10 s startup budget matters: the server must come up fast and must not wait for MuseScore at startup.
- **Claude Desktop.** macOS, Windows, Linux (beta since July 2026, Ubuntu 22.04+/Debian 12+, apt repo). Config: `~/Library/Application Support/Claude/claude_desktop_config.json`, `%APPDATA%\Claude\claude_desktop_config.json`; the Linux path is undocumented (community: `~/.config/Claude/`). Restart needed on config change; server stderr goes to `mcp-server-<name>.log`. Every tool call needs approval unless the user clicks "Allow always"; its persistence across sessions is reported as unreliable.
- **Claude Code.** `.mcp.json` project scope (approval prompt the first time, `claude mcp reset-project-choices`); `claude mcp add [-s local|project|user] [-e K=V] <name> -- <cmd>`; `--mcp-config` (waits up to `MCP_TIMEOUT`, 30 s) with `--strict-mcp-config`; `-p --output-format json|stream-json`, `--json-schema`, `--max-turns`, `--max-budget-usd`, `--permission-prompts none`, `--allowedTools "mcp__reflets__*"` (globs only after the literal `mcp__<server>__` prefix), `--disallowedTools "mcp__*"`. `--bare` skips discovery but does not use the subscription login. Tool names over 128 chars are dropped. Subscription runs of `claude -p` count against plan limits, not per-run billing.
- **MCP SDKs.** Python SDK v2.3.0 (2026-10-02): `FastMCP` renamed `MCPServer`, stdio server diverts stray stdout to stderr, raise `ToolError` for model-visible errors (other exceptions become "Error executing tool"), Python >= 3.11, structured output validated. The sheet-music-plugin already depends on `mcp>=2.2`. TypeScript SDK v2.3.1: split packages, ESM-only, Node 20+. Spec 2026-07-28: no `initialize` handshake, mandatory `server/discover`, Multi Round-Trip Requests (`InputRequiredResult`) replace sampling/elicitation requests, roots/sampling/logging deprecated, `resultType` required, `ttlMs`/`cacheScope` on list results. Decision follows: **Python server**, importing the engine in-process.
- **Licensing.** MuseScore's own handbook: "You own what you create"; opening in MuseScore or writing QML does not bind a plugin to GPL. mcp-score and ghchen99 are MIT with WebSocket QML plugins. The bundled `dev_test_websocket.qml_disabled` sample is GPL-3.0: do not copy it. Recommendation: plugin and server MIT, plugin written from scratch against the public API.

### Test rig facts (local agent)

- **No report exists of MuseScore 4 under WSLg.** Adjacent evidence: from 4.6 on `main.cpp` forces `QT_QPA_PLATFORM=xcb` unless `MU_QT_QPA_PLATFORM` is set, so under WSLg the AppImage goes to XWayland (DISPLAY=:0) by default, which is the better path. For offscreen or wayland set both `QT_QPA_PLATFORM` and `MU_QT_QPA_PLATFORM`. Qt Quick apps under WSLg may render one black frame without `LIBGL_ALWAYS_SOFTWARE=1` (wslg issue #1025); `QT_QUICK_BACKEND=software` is the MuseScore forum workaround for rendering glitches. AppImage needs libfuse2 (not installed here) or `--appimage-extract` then `squashfs-root/AppRun`. WSLg has PulseAudio. The 4.7.5 Linux build is `MuseScore-Studio-4.7.5.260831071-x86_64.AppImage` on the GitHub release.
- **Offscreen** works for converter mode (`-o`) since 4.1 (`QT_QPA_PLATFORM=offscreen`, plus `MU_QT_QPA_PLATFORM` from 4.6). Untested for the GUI mode the WebSocket bridge needs; mcp-score uses Xvfb for the GUI. Both modes need a Qt platform plugin.
- **CLI.** No `-p`/plugin option in 4.x (handbook page is stale, copied from 3.x). `--extension <uri>` with `-o`/`-j` exists since 4.5 but issue #24187 reports it does nothing for a plugin. `-j` job keys: `in`, `out` (string, array, or `[prefix, suffix]` per part), `transpose`, `page`, `visibleParts`, `copyright`, `tracksDiff`. Exit code 0 on success (`Ret::Ok`), 1 unknown error, 3 cancel, 4 not supported, 6 bad data.
- **`.mscz`** is a zip with `<name>.mscx` (plain XML), `<name>_style.mss`, `Thumbnails/`, `audiosettings.json`, `viewsettings.json`, `Excerpts/`. `unzip -p x.mscz score.mscx` gives diffable XML. `musicdiff` 6.0 diffs notation semantically across MusicXML/kern; Verovio converts to MEI.
- **WSL2 mirrored mode.** Documented: Linux reaches Windows servers at 127.0.0.1 (not ::1); loopback between host and WSL is allowed by default (`LoopbackEnabled`); a port bound on Windows is not bindable in Linux unless listed in `ignoredPorts`. Open WSL bugs (#40343, #41102) report 127.0.0.1 handshakes failing in mirrored mode on some builds; test with `nc -vz 127.0.0.1 <port>` first. Use the literal `127.0.0.1`, not `localhost`.
- **Model-free MCP testing.** Inspector CLI: `npx @modelcontextprotocol/inspector --cli <cmd> --method tools/call --tool-name X --tool-arg k=v --format json` (exit 5 when the tool returns isError). Python SDK: in-process `Client(app)` (v2) or `stdio_client(StdioServerParameters(command, args, env))` + `ClientSession` for pytest. Model-in-the-loop: `claude -p` with `--mcp-config` (stdio spec accepts `env`), `--strict-mcp-config`, `--allowedTools`, `--output-format json` (reports `total_cost_usd` as an estimate; subscription usage counts against plan limits).
