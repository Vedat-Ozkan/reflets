## 1. Scope

In scope for the core:

1. **Bridge plugin**: one QML file installed in the user's MuseScore plugin folder. It has no window (2.1), listens on a local WebSocket port, and executes read and write requests against the open score.
2. **MCP server**: a Python package the user's harness starts over stdio. It owns the connection to the plugin, converts between the two wire protocols, calls the analysis engine, and exposes fewer than ten tools.
3. **Protocol A**: plugin to server. Line-oriented text with request ids, an application-level ping, and client-side reconnect.
4. **Protocol B**: model to server. The N1 compact note list from the engine, extended with rests, part identity, dynamics and chord symbols. The same grammar is used for reading and for writing ideas.
5. **Write path**: one undo step per idea, verified by read-back.
6. **Ideas into MuseScore**: in place (one undo step) and as a new tab built from a temporary MusicXML file.

Out of scope here: the critic, teacher, collaborator and assistant prompts (`notes:83-86`); the AnalysisGNN draft and PDF reading (`notes:67-68`); any UI inside MuseScore beyond the bridge window (`plan:14`); the full verification rig (`plan:134`, outlined in section 9 only as far as it constrains the design).

## 2. Placement decisions

### 2.1 The plugin is a legacy v1 QML plugin without a dialog

- A v1 plugin gets exactly `api.log`, `api.engraving`, `api.websocket`, `api.websocketserver` (`api:90`). That is everything the bridge needs; the v2 extension API adds interactive and theme objects and deliberately omits process and filesystem (`api:92`), so v2 buys nothing for the bridge and costs a manifest.json.
- Manifest: no `pluginType` (a "macro" plugin), `requiresScore: false` (`api:114`: `"false"` maps to UI context `Any`). The manifest is a line scan of the `MuseScore {` block, so these properties are written as plain literal lines (`api:114`).
- **Why no dialog** (spike, `research/spike-bridge-hello-2026-10-18.md`, round 3): while a v1 plugin's dialog is open, MuseScore refuses every notation action gated on the score page being current. `cmd("tie")` logs `no one can handle the action: tie` with the dialog open, inside or outside `startCmd`, and works with no dialog open. Undo and redo are not affected (own enabler). So a dialog bridge cannot tie, and probably cannot dispatch most other notation actions.
- Lifecycle: a macro plugin is created by `component.create()` and then never deleted (`src/framework/extensions/internal/legacy/extpluginrunner.cpp:49-61` at v4.7.5), so its object, and the server it started in `onRun`, live until MuseScore quits. The plugin is started once per session from the Plugins menu and cannot be stopped except by quitting MuseScore. This relies on the runner not deleting the object, which is unspecified behaviour; recheck on each new MuseScore release.
- One server per MuseScore: all v1 plugins share one `WebSocketServerApi` object (`src/framework/network/api/websocketserverapi.cpp` at v4.7.5). A second `listen()` on another port fails silently but replaces the new-connection callback, so the most recently started plugin answers new connections. Running the bridge twice is harmless (the new instance takes over); running another bridge plugin (mcp-score, ghchen99) in the same session steals the connection, which `hello` detects.
- Qt 6 and QtQuick.Controls 2 idioms only, because a plugin not written for Qt 6 is silently not listed (`deep:49`, `deep:56`).
- No status window. Status is reported through `hello` and the server's tool errors; `api.log.info` lines go to MuseScore's log file.

### 2.2 The plugin listens, the server connects

`api.websocketserver` has `listen`, `onMessage`, `send` and nothing else: no close, no disconnect callback, text frames only (`deep:6`). The research's own conclusion is adopted: the plugin is the listener and the MCP server is the reconnecting client (`deep:13`).

Port: the API default is 8084 when the port is negative (`deep:6`); mcp-score and ghchen99 both use 8765 (`notes:157`, `deep:93`). Reflets uses its own default, **8731**, a constant in the plugin file and settable on the server (`REFLETS_PORT`). Reason: a stale plugin instance keeps serving its port after a restart (`deep:81`), and a stale mcp-score plugin on 8765 would otherwise answer a Reflets connection with the wrong protocol. The `hello` handshake (3.5) identifies the plugin in any case.

Security: `listen()` binds all interfaces, not loopback (`deep:6`). On the owner's machine Windows already had inbound Allow rules for MuseScore 4 on the Public profile, so no prompt appeared and other devices on the network can likely connect. Decided 2026-10-18 (open question 4): a shared secret. At `onRun` the plugin writes a random token to a file under Documents/MuseScore4 with `FileIO` (`api:20`); the server reads it and sends it in `hello`; the plugin answers nothing else on a connection until a matching `hello`. No TLS, no accounts.

### 2.3 Music logic lives in Python, the plugin stays thin

- Plugin code is cached at MuseScore startup, so every plugin change costs a MuseScore restart (`deep:81`, `deep:89`).
- Plugin `console.log` output is discarded (`deep:28`); diagnostics must go over the socket.
- The Python side can be tested in-process with the SDK client (`rig:41`) and from the Inspector CLI (`rig:40`).

Rule: the plugin does only what requires the PluginAPI (walk the score, place notes, run commands) and emits a raw line format that mirrors the API's fields (3.7). All conversion to and from the model-facing format, all validation, all caching and all music reasoning are in the server.

### 2.4 The server is Python, importing the engine

- Python MCP SDK v2.3.0 (2026-10-02): `FastMCP` is now `MCPServer`, stdio servers divert stray stdout to stderr, `ToolError` carries a model-visible message, Python >= 3.11 (`hosts:50`). The engine already depends on `mcp>=2.2` and Python >= 3.11 (`engine:147`). Decision recorded in the plan: Python server importing the engine in-process (`plan:97`).
- The engine's N1 encoder and decoder are stdlib-only (`engine:17`), and a decoded N1 index works with `part_writing.check`, `draft.build`, `harmony` and `reduce.as_text` without MusicXML (`engine:48`, `engine:50-55`). This is the path the critic uses on live reads.

### 2.5 Supported MuseScore versions

- Official 4.7 builds, tested on 4.7.5 (owner decision, 2026-10-18). The WebSocket API exists from 4.4.2 (`deep:17`, `deep:24`), but 4.4.3 stubs `readScore`/`writeScore` (`api-gaps` 3.2) and the undo codes differ before 4.7 (6.8), so older versions are refused at `hello` rather than half supported. The plugin checks `api.websocketserver` at start and shows a message if it is undefined, which happens in some distro builds (`deep:17`, `deep:24`).
- GUI only: the console and `--extension` contexts have no WebSocket API on 4.7 (`deep:28`, `deep:34`).
- The owner's Windows install is 4.7.5, where the bridge spike passed (`research/spike-bridge-hello-2026-10-18.md`). Test matrix: 4.7.5.
- Version is read from `mscoreVersion` (major*10000 + minor*100 + patch, 40705 for 4.7.5; `api:21`) and reported in `hello` so the server can refuse unknown versions with a clear message.

## 3. Protocol A: plugin to server

### 3.1 Transport

WebSocket, text frames only (`deep:6`). The server connects to the literal `ws://127.0.0.1:<port>`, never `localhost`, because under WSL2 mirrored networking only 127.0.0.1 is documented and `::1` is not supported (`rig:27`, `rig:30`).

Found in the element spike (2026-10-19): `api.websocketserver` is shared by every plugin in the MuseScore process, and the last plugin to call `listen` receives every connection, whatever port it listens on. Another plugin that uses the WebSocket server, run after the bridge, takes Reflets' connections; `doctor` (5.2) should detect a reply that is not the bridge's `hello`.

### 3.2 Framing

One WebSocket frame is one message. A message is UTF-8 text split on `\n`. Line 1 is the header. Lines 2 onward are the body. Text fields (titles, annotation text) are always the last field of their line and are escaped: `\` becomes `\\`, newline becomes `\n`.

```
request   <id> <verb> [<arg> ...]
          <body line>*
response  <id> ok [<summary> ...]
          <body line>*
          <id> err <code> <message>
```

- `<id>` is a decimal integer, increasing per connection, starting at 1. The plugin echoes it. The server discards any response whose id it is not waiting for, which happens after a reconnect, since the plugin cannot observe disconnection and has no close method (`deep:6`, `deep:13`).
- One request is in flight at a time. The plugin is single-threaded QML and the server serialises its queue. The id exists to detect stale replies, not to multiplex.
- Why a line format and not JSON: the read body is already a line-per-event list that the server turns into the model-facing N1x (section 4), and the compact format is about ten times smaller than minified JSON-per-note (`plan:54`, `plan:56`). Keeping the plugin's output line-oriented means no double encoding and no JSON builder in QML. JSON would have worked over text frames too; this is a cost choice, not a capability one.

### 3.3 Liveness: application-level ping

As built in slice 1 (2026-10-18): no ping loop. The server connects on the first tool call and, if a request fails on a dropped socket, reconnects once (3.4) before reporting that MuseScore is not reachable. The ping loop below waits until something needs it. The plugin registers `onMessage` once per connection, in its new-connection callback, which runs once per client id; and it admits a connection only after a `hello` with the token (2.2).

- The server sends `ping` every 5 s while idle and treats two missed `pong`s as a dead connection, closes its socket and reconnects. The API offers no disconnect callback and no close, so liveness can only be detected at application level (`deep:13`); mcp-score polls a ping every 2 s for readiness (`deep:93`).
- The plugin registers `onMessage` once per client id (ids start at 2001; `deep:6`); registering twice double-delivers messages (`deep:6`, `deep:13`). The plugin keeps a set of ids it has registered.
- The plugin cannot drop a client. It keeps the id map and answers whoever speaks. The server's hello (3.5) is the only admission control in v1.

### 3.4 Reconnect: client side, never blocking startup

As built in slice 1: no state machine or backoff; connect lazily on the first tool call (which already keeps startup instant, about 0.4 s to import), one retry per request. `score_info` returns the not-reachable text as its result; the other tools raise it as `ToolError`.

- Server states: `disconnected`, `connecting`, `hello`, `ready`. Backoff 0.5 s, 1 s, 2 s, 5 s, then 5 s steady.
- The server never waits for MuseScore at startup. Codex kills a server that takes more than 10 s to start (`hosts:19`) and Claude Code waits at most `MCP_TIMEOUT`, 30 s, for pending servers (`hosts:37`). The process must answer the MCP handshake within a second and connect to the plugin in the background.
- A tool called while not `ready` raises `ToolError` with the user-facing instruction "open MuseScore, open your score, run Plugins > Reflets Bridge" (`hosts:50`: `ToolError` reaches the model; other exceptions are flattened to "Error executing tool").

### 3.5 Handshake

```
1 hello proto=1 client=reflets-server/0.1
1 ok proto=1 plugin=reflets-bridge/0.1 mscore=40705 score=1 title=Nocturne\ in\ E\ flat
```

- `mscore` is `mscoreVersion` (`api:21`). `score=0` when `curScore` is null (`api:11`).
- A `proto` mismatch produces a server-side message telling the user to update the plugin file and restart MuseScore, because the plugin is cached at startup (`deep:81`).
- The plugin picks its action-code table (6.8) from `mscoreVersion` at hello time.

### 3.7 Read body: raw event lines

The plugin emits one line per API object it visits. Field order is fixed; unknown trailing fields are ignored by the server so fields can be added without a protocol bump.

```
T <title>                                      metaTag("workTitle")           api:36
P <partIdx> <startTrack> <endTrack> <instrumentId> <longName>                 api:70
S <staffIdx> <partIdx> <clefType@0> <lines>                                   api:69
M <no> <irregular> <tick> <ticks> <actN>/<actD> <nomN>/<nomD>                api:66, src:85
K <tick> <staffIdx> <key>                      Staff.key(frac) at bar start   api:69
C <tick> <track> <z>/<n> [T<a>:<b>] [G<noteType>] [!<artic>,..] <note>[,<note>..]
R <tick> <track> <z>/<n> [T<a>:<b>]
A <tick> <track> <kind> <text>
H <no> <hash>
```

- `C` is a chord (one or more notes at one onset in one voice). `<note>` is `<pitch>:<tpc1>:<tpc2>[:b][:f]`: MIDI pitch, concert tonal pitch class, written tonal pitch class, tie-back flag, tie-forward flag. The pitch is the sounding pitch: `Note.pitch` excludes octave lines, so the plugin adds `Staff.pitchOffset(tick)` (since 4.6); without it, 8va passages read an octave low (slice 1, compared against the engine's N1 of the nocturne). A write under an octave line must subtract the offset again. Sources: `Chord.notes` (`api:63`), `Note.pitch/tpc1/tpc2/tieBack/tieForward` (`api:60`). The tonal pitch class is what distinguishes C sharp from D flat, which harmony analysis needs and which MIDI pitch alone loses (`notes:173`); the engine keeps spelled pitch (`engine:11`).
- `<z>/<n>` is `DurationElement.duration` as numerator and denominator (`api:61`); `T<a>:<b>` is `Tuplet.actualNotes:normalNotes` (`api:64`, there is no ratio property). `G<noteType>` marks a grace note by `Note.noteType` (`api:60`); grace chords come from `Chord.graceNotes` (`api:63`) and are emitted before their parent chord with the parent's tick.
- `!<artic>` lists `Chord.articulations` by name (`api:63`). Carried in the raw format for later use; not in N1x v1 (4.2).
- `A` kinds: `dyn` (`dynamicType`), `harm` (`harmonyType` plus `text`), `text` (staff text), `tempo` (`tempo`, `text`), all from `Segment.annotations` as generic items with those properties (`api:59`, `api:65`), typed by `ScoreElement.name` (`api:58`). Lyrics (`ChordRest.lyrics`, `api:62`) are not emitted in v1; as built in slice 3 they are, as `Y` lines (4.2).
- `M` carries `no` and `irregular` (`api:66`). The on-screen number is `no + 1`, `noOffset` is already folded into `no`, and an irregular bar does not advance the count, so a pickup shares its `no` with the bar after it and the server labels it bar 0 (`src:85-86`, `src:90`). Confirmed against the screen in spike 5.
- Ticks are integers (`Segment.tick`, `api:65`); the server converts to quarter-note offsets with the `division` constant (`api:21`), which is sent once in `info`.
- As built in slice 3 (protocol 3): `info` also sends `X composer <text>`; `M` gains `<repeatStart> <repeatEnd> <repeatCount>`; after each `M`, `B <tick> <barlineType>` for an end bar line on staff 1 the user set (not `generated`), `L <tick> <layoutBreakType>`, `J <tick> <jumpTo> <playUntil> <continueAt> <text>` and `Q <tick> <markerType> <label> <text>` from `Measure.elements`; at the end, `V <tick> <ticks> <endings> <text>` per volta from `Score.spanners`. One-word fields write a space as `\s` and an empty value as `-`. As built in slice 3, marks (protocol 4, plugin 0.4.0): `A <tick> <track> <name> <value> <text>`, where `<name>` is `ScoreElement.name` and `<value>` is `dynamicType`, `harmonyType`, `tempo` (beats per second) or `playTechType`, else 0; `F <tick> <track> <concertClefType>` for each clef change, from Clef segments only (not header clefs, not generated clefs). A clef change at a bar start lives at the end of the bar before, so `read` also visits the bar before its range for clefs at the range's first tick. Decorations (protocol 5, plugin 0.5.0): between the flags and the notes, a `C` line may carry `!<symbol>,…` (`Chord.articulations`, which in 4.7.5 holds ornaments too, by `SymId` name, mapped from the number through the plugin's `SymId` enum), `A<arpeggioType>`, `M<tremoloType>` (single-chord tremolo), `S<stemDirection>`, `B<beamMode>` and `X<staffMove>` where not 0; the notes are always the last word. A note gains `:l` for a laissez vibrer, which 4.7.5 returns as `tieForward` named `LaissezVib` and which earlier protocols read as a tie, `:p` for parentheses, `:h<headGroup>` where not 0 and `:F<fingering>` (URI-encoded) per fingering. Fermatas come as `A <tick> <track> Fermata <symbol>` and breath marks and caesuras, elements of a Breath segment, as `A <tick> <track> Breath <symbol>`. Groups (protocol 6, plugin 0.6.0): the tuplet flag becomes `T<a>:<b>:<z>/<n>`, one per tuplet level, outermost first, where `<z>/<n>` is `Tuplet.duration`, the tuplet's whole length in the written values of the level above (`api:61`, `api:64`); without it, two 16th triplets and one eighth triplet of six 16ths read the same. MuseScore rounds the ticks of notes whose position is not a whole number of ticks (inside a triplet inside a triplet, `8427`), so the server takes an onset within one tick of the end of the voice's previous note or rest as that end. Lines (protocol 7, plugin 0.7.0): after the bar's elements, `N <tick> <end> <track> <track2> <name> <sub> <text>` for each spanner of `Score.spanners` that starts or ends in the range, voltas aside (they stay in `info`), where `<name>` is `ScoreElement.name` (`Slur`, `HairPin`, `Pedal`, `Ottava`, `Trill`, `Vibrato`, `LetRing`, `PalmMute`, `TextLine`, `GradualTempoChange`, …), `<sub>` is `hairpinType`, `ottavaType`, `trillType`, `vibratoType` or, for a text line, 1 for a system text line, else 0, and `<text>` is `beginText`. `<end>` is `spannerTick + spannerTicks`, except for a slur or hammer-on, whose ticks end at the start of its last chord: there it is the end of that chord, or the chord's own tick with a `g` suffix (`960g`) when the slur ends on a grace note before its main note. A note gains `:g<glissType>` for a glissando that starts on it (`Note.spannerForward`).
- Transposing instruments: the server derives spelled sounding pitch from `pitch` and `tpc1` (concert), matching the engine, which analyses at sounding pitch (`engine:11`); `tpc2` is kept so a write-back can set both.

**Fingerprint `H` lines.** There is no change signal: `scoreStateChanged` is declared but never emitted anywhere in the repository (`api:9`, `api:126`), and the claim that it works was refuted 0-3 (`deep:150`). The fallback named in the notes is polling or a "check now" (`notes:183`). Reflets does "check now" on demand: at each tool call the server requests `fp`, compares per-measure hashes with its cache, and re-reads only the measures that changed. That meets the no-full-re-reads target (`plan:12`). The hash is djb2 over the measure's `C`, `R`, `A` lines across all tracks, computed in the plugin so only one short line per bar crosses the socket. **[spike]** time the `fp` walk on a 300-bar orchestral score; it runs on MuseScore's UI thread.

### 3.8 Write body: ops

Writes are sequential per voice and bar, in note-entry order, because the cursor only lands reliably where its track already has content and advances by itself after each entry (`src:35`, `src:43-44`, `src:56`).

```
v <track> <barTick>            start a voice pass: land at the bar in voice 1 of the staff, then switch to <track>
d <z>/<n>                      duration for the entries that follow
n <note>[,<note>..]            chord at the cursor, <note> = <pitch>:<tpc1>:<tpc2>; advances the cursor
r                              rest at the cursor; advances
t <a>:<b> <z>/<n>              tuplet of a:b over total duration z/n, followed by its n and r entries
a <track> <tick> <kind> <text> dyn | harm | text, after all voice passes
~ <track> <tick> <pitch>       tie the note at (track, tick, pitch) forward, last
g <track> <tick> <kind> <note> grace note on the chord at (track, tick); kind is the action code
                               (acciaccatura, appoggiatura, grace4, grace16, grace32, grace8after, ...)
```

Execution order inside one `write`: the `v` passes in track order, each a run of `d`, `t`, `n`, `r` lines that must fill the bar exactly (`src:58`); then a spelling pass that revisits each written chord by tick to set `tpc1` and `tpc2` (`src:59`); then `a`; then `~` last, because a tie needs both notes to exist (6.5). The server compiles N1x into this list; the plugin never parses music, only ops.

As built in slice 2: `n <tick> <pitch>:<tpc1>[,...]` and `r <tick>` carry the tick the server computed, so the spelling and colour pass finds each chord by tick, not from the cursor. The plugin keeps the instrument's transposition when spelling (`tpc2 = tpc1 + (old tpc2 - old tpc1)`) and subtracts `pitchOffset` (3.7); the transposition part is untested, since the test score is for piano. Live test: `tests/live_write.py`. Order: voice passes, spelling and colour, `g`, `~`. `t` and `a` are not compiled yet: ideas with tuplets, dynamics or chord symbols are refused. As built in slice 4, first step (protocol 9, plugin 0.9.0): `t <a>:<b> <z>/<n>` is compiled; it calls `cursor.addTuplet` at the cursor, `<z>/<n>` being the tuplet's whole span in written whole notes of its context (inside an outer tuplet, scaled by that tuplet's ratio), and the `d` values after it are written values (actual time × a/b for every enclosing tuplet). Nested tuplets and rests inside tuplets work through the same op. `g` takes a grace chord, `g <track> <tick> <kind> <note>[,<note>..]`: the first note comes from the grace action as before, each further note is a `newElement(NOTE)` added to the new grace chord with `Chord.add`. Second step (protocol 10, plugin 0.10.0): `x <track> <startTick> <endTick>` runs before the voice passes and removes, with `removeElement`, every annotation of that track in the range except fermatas, and for a voice-1 track the clefs the user set in that staff, including one at the range's start that MuseScore keeps at the end of the bar before; one undo restores them all, though `Segment.annotations` then lists a segment's annotations in another order. `a <track> <tick> <kind> <value> <text>` runs after the grace notes: `kind` names the `Element` type (`DYNAMIC`, `HARMONY`, `TEMPO_TEXT`, `STAFF_TEXT`, `SYSTEM_TEXT`, `EXPRESSION`, `REHEARSAL_MARK`, `PLAYTECH_ANNOTATION`, `FIGURED_BASS`, `CLEF`), `value` the dynamic type, tempo in beats per second or clef type, and `text` the rest of the line with `\\` and `\n` escaped. The cursor is placed at the tick in the mark's track, else in any track with a segment there; with none, the write fails. Text is set after `cursor.add`; tempo is set before and again after the text, with `tempoFollowText` off; a clef gets `concertClefType` and `transposingClefType` before the add. Marks are coloured like the idea's notes, and `keep` turns a voice's annotations black too. Third step (protocol 11, plugin 0.11.0): `e <track> <tick> <pitch|-> <what> <value>` adds a decoration after the marks: `art` (an articulation, or an ornament when the `SymId` name starts with `ornament`, through `Chord.add` without setting `track`), `arp` and `trem` (`arpeggioType`, `tremoloType`, `Chord.add`), `move` (`staffMove`), `fermata` (an annotation at the chord or rest through the cursor) and `breath` (through the cursor at the tick the breath stands at, the end of the note or rest it follows), and on one note `head` (`headGroup`), `finger` (`Note.add` of a FINGERING, text after), `lv` (`cmd("lv")`) and `paren` (`cmd("add-parentheses")`) with the note selected. A `SymId` name MuseScore does not have fails the write. `g` takes a grace type as its action (`appoggiatura`, `grace8after`, …) and a fingering per note as `:F<text>`, URL-encoded. `x` takes a fourth field, 1 when the voice's notes are rewritten: then it also removes the voice's grace notes, which note entry leaves on the new chord at the same tick (they doubled when a voice with grace notes was rewritten, a slice 4 first-step bug), and its tuplets, which `addTuplet` cannot rebuild in place (writing a tuplet over the same tuplet failed). It now removes fermatas and breaths too, and, like `read`, only the clefs of the bar before the range, not its other segments: an annotation MuseScore keeps on the previous bar's last segment at the range's start tick was removed and came back in the wrong bar on undo. `~` takes the tick of the note it ties to when that note lies in the bar after the idea; the plugin checks the note is there, since the tie action otherwise adds a new note. Fourth step (protocol 12, plugin 0.12.0): `x` also removes the spanners, voltas apart, that start in its track and range or end there in their end track (`spannerTrack2`), the end computed as `read` computes it; system lines only for track 0. `l <track> <tick> <track2> <endTick> <grace 0|1> <ELEMENT> <subtype> <text>` adds a line. A slur goes through `add-slur` over a list selection of its first note and its last: the chord in the end track that ends at `endTick`, or with grace 1 the last grace note before the chord at `endTick`; a slur that would start and end on one chord starts on that chord's first grace note. It is then `escape`d and coloured. Any other line is a new element with its subtype property set first (`hairpinType`, with the `cresc.`/`dim.` begin and continue texts for those two, `ottavaType`, `trillType`, `vibratoType`) or its `beginText`, then `spannerTick`, `spannerTicks` and `spannerTrack2`, then `cursor.add` with the cursor at the start of the bar the line starts in, which needs no note or rest at the line's own tick. Octave lines are added right after the clears and before the notes, since note entry subtracts the staff's pitch offset at the note's tick; the other lines come last. `keep` turns the lines that start or end in the kept voices black too. Keeping details, first stage (protocol 13, plugin 0.13.0, decision 32): `x` no longer removes annotations, clefs, fermatas or breaths, only spanners, and with notes=1 grace notes and tuplets; a spike on 2026-10-20 showed that note entry over a voice keeps a segment's annotations, fermatas and breaths at their tick even when no note starts there any more (they read back with `@`), and keeps hairpins, pedal lines, ottavas and grace notes, while it loses articulations and the chord's other children, deletes a slur whose end chord is overwritten, and garbles a tuplet it overwrites in part. `y <line>` removes the one annotation, clef or breath whose `read` line is exactly `<line>`; it runs before the notes. Second stage (protocol 14, plugin 0.14.0): `x` is sent only for a voice whose notes are rewritten and removes only its grace notes and tuplets; `z <tick> <track> <endTick> <name>` removes the one spanner with that MuseScore name, start, track and end (as `read` computes it), and all `z` ops run first, since removing grace notes or tuplets deletes the slurs on them. Lyrics (protocol 15, plugin 0.15.0): `w <track> <tick> <verse> <continues 0|1> <bound> <text>` sets a syllable on the chord at that tick, replacing one of that verse it has: a new `LYRICS` element with `verse` set, `cursor.add`, then `text`, then `syllabic` from its own continuation and that of the verse's previous syllable in the track (found by walking back through the segments), then `lyricTicks` from the last chord of the track starting after it and at or before `bound` (0 when there is none), so a hold is given as a tick bound and lands on a chord. `u <track> <tick> <verse>` removes the syllable; `h <track> <tick> <verse> <bound>` resets the hold of the verse's last syllable at or before `tick`, which may lie before the idea. They run after the ties, removals first, then the syllables in tick order, then the holds. The syllable after the idea keeps its own `syllabic`. Syllables take the idea's colour and `keep` turns them black. Ties into the idea (protocol 16, plugin 0.16.0): `^ <track> <tick> <pitch>` ties the note of that pitch on the chord before `tick` in the track, found by walking back through the segments, to the new note at `tick`, through the tie action; it runs with the other ties. Bar fields (protocol 17, plugin 0.17.0): `b <tick> <change>` changes the bar at that tick, after the ties: `rep <start> <end> <count>` sets `repeatStart`, `repeatEnd` and `repeatCount`; `bar <type>` sets `barlineType` on every staff's end bar line (1, normal, to remove one); `break+ <type>`, `jump+ <jumpTo> <playUntil> <continueAt> <text>` and `mark+ <markerType>` add a layout break, jump or marker through the cursor on track 0 at the bar's start, labels as one-word fields; `break-`, `jump-` and `mark-` remove the matching element of `Measure.elements`; `volta-` removes the volta over the tick. A new volta is an `l` op with `VOLTA` and its text (decision 28). MuseScore adds a play count text (`3x`) of its own when a repeat count changes, and lays it out again after an undo even where the score had none, so `read` skips `PlayCountText` annotations. Bar-level elements are not coloured. Meters (protocol 18, plugin 0.18.0): `b <tick> meter <n> <d>` adds a `TIMESIG` with `timesig` set through the cursor on track 0 at the bar's tick and never touches the element again (3.8, `cmdAddTimeSig` deletes it); `b <tick> meter-` removes the bar's time signature. They run first, so the first op loop also takes `b` ops. `cmdAddTimeSig` and the removal rebuild every bar up to the next meter change, even at the same length: on the nocturne, text kept its words but lost its formatting (`<i>simile</i>` became `simile`), an `fp` dynamic's text became `z`, and slurs ending on grace notes moved to the main note. So around a meter op the plugin notes the text of every annotation from the bar before on (by tick, track, name and order) and sets back any that changed, and removes and adds again, in black, each slur that ended on grace notes and no longer does. Keys (protocol 19, plugin 0.19.0): `b <tick> key <concertKey>` adds on every staff a `KEYSIG` with `concertKey` and `actualKey` set before `cursor.add` on the staff's first track, the written key being the concert key plus the difference between `actualKey` and `concertKey` of the staff's key signature in effect there (two sharps for a B-flat clarinet), kept within seven sharps or flats; a key signature already at that tick is removed first. `b <tick> key-` removes the key signature at that tick on every staff. Checked live on `tests/data/keys.musicxml`, a B-flat clarinet over a piano: E-flat major gives the clarinet one flat and the piano three.

### 3.9 Error codes

`no-score` (`curScore` null, `api:11`), `bad-request`, `unsupported` (verb not available on this version), `write-failed <opIndex> <why>` (rolled back), `verify-failed <firstMismatch>` (rolled back), `export-failed`, `open-failed`. Every `err` on `write` means `endCmd(true)` was called and the score is as it was (`api:31`).

### 3.10 Sizes

The server reads in windows of bars (4.4), so one response is one frame of at most a few thousand lines. The 38-bar Chopin nocturne, 1,253 notes, is about 1,300 `C` lines in this format; the N1 version of the same bars is 5,796 characters (`plan:54`). No chunking protocol is needed in v1.

## 4. Protocol B: model to server (N1x)

### 4.1 Base: N1

The engine's N1 note list (`engine/notes.py`) round-trips through `encode`/`decode` (`engine:75`), keeps spelled pitch, staff and voice, grace notes, ties, chords, bar numbers including a pickup, bar length, meter changes and the first key signature (`engine:61-65`), and is stdlib-only by design so the model's environment can import it (`engine:17`). On the Chopin measurement it is 5,796 characters against 58,745 for minified JSON-per-note and 509,478 for MusicXML (`plan:49-54`). The directional evidence that compact text beats event-per-token formats is ABC at about 38% of MIDI-event token length (`deep:116`), with the caveat that Reflets must measure its own encoding with Claude's tokenizer on polyphonic scores (`deep:121`).

### 4.2 Extensions: N1x

N1 drops rests, part identity, clefs, key changes, slurs, dynamics, articulations, lyrics, chord symbols and tuplet markup (`engine:68-71`). N1x carries every element a MuseScore user can read and write (open question 17), as additions to N1's grammar (`src:94-95`). Plain N1 stays valid for its existing callers (`src:100`); the header tag `N1x` marks the extended text. Decided 2026-10-19 with the owner after the element survey (`research/musescore-4.7.5-element-coverage.md`) and the compression study (`research/encoding-compression-2026-10-18.md`); not built yet.

Illustration (the nocturne's opening; slur and pedal placement is made up):

```
N1x div=48 ts=12/8 ks=3f
title="Nocturne Op.9 No.2" composer="Chopin"
P1 "Piano" staves=1-2 instr=piano
m0 len=24
1.1: q60 s"Andante" x"espress. dolce" !p 24 Bb4
2.1: 24 r
m1 len=288
1.1: ( 72 G5~ 24 G5 F5 G5 ) ( 72 F5[ten] 48 Eb5 24 Bb4 )
2.1: ped( 24 Eb2 G3+Eb4 Bb3+Eb4+G4 ped)@72 ped( 24 Eb3 ...
m9 = m1
```

**Header lines**, after the version line: `title="…"`, `composer="…"` (score metadata), and one `P<n> "<name>" staves=<a>-<b> instr=<instrumentId>` per part. Quoted text escapes `"` as `\"`.

**Bar line fields**, on the `mN len=` line: `ts=` and `ks=` where the meter or key changes (open question 12); `rep=start|end|both` and `x=<count>` for repeats; `volta=1` or `volta=1,2` on each bar under an ending (consecutive bars with the same value are one volta); `bar=double|final|dashed|…` for a bar line the user set; `break=line|page|section`; `jump=<type>` (D.C., D.S. al Coda, … by MuseScore's jump type) and `mark=segno|coda|fine|tocoda|…`.

**Marks at a moment**, written just before the note or rest they fall on, or after a note with `@<offset>` (in `div` units from the bar start) when they fall inside it (open question 18): `!mf` dynamic, `"G7"` chord symbol, `x"…"` expression, `s"…"` staff text, `S"…"` system text, `q60` or `q60"Andante"` tempo in quarter notes per minute, `R"A"` rehearsal mark, `fb"6/4"` figured bass, `pt"pizz."` playing technique, `clef=bass` clef change. Tempo, rehearsal marks, system text, jumps, markers and voltas are system objects that MuseScore keeps on track 0, so they appear in staff 1 voice 1.

**Lines** with a start and an end, in the voice line of their track: `( … )` slur; `<( … <)` crescendo and `>( … >)` diminuendo hairpin; `cresc( … cresc)` and `dim( … dim)` text lines; `ped( … ped)` pedal; `8va( … 8va)`, also `8vb`, `15ma`, `15mb`, `22ma`; `tr( … tr)` trill line; `vib(`, `lr(` (let ring), `pm(` (palm mute); `line"text"( … line)` text line. An opener goes before the note the line starts on; a closer after the note it ends with (the line ends at that note's end), or with `@<offset>`. Lines may cross bars. Pitches stay sounding pitches under octave lines.

**Decorations of a note or chord**, in brackets right after it: `G5[stacc,acc]`, `Eb4+G4[arp]`. Short names for the common ones (`stacc`, `staccis`, `ten`, `acc`, `marc`, `port`, `fermata`, `breath`, `caesura`, `arp`, `arp-up`, `arp-down`, `tr`, `mord`, `prall`, `turn`, `trem8` to `trem64`, `lv`, `paren`), MuseScore's own symbol name for any other (`[articStressAbove]`), so nothing is lost. Engraving choices appear only where the user changed MuseScore's default: `up`/`down` stem, `beam=none|start|mid|…`, `head=x|…`, `staff+1`/`staff-1` cross-staff. Grace types other than the default (a single grace is an acciaccatura, a group 16ths) go on the grace token: `gD5[appog]`, `gD5[after]`. Fingering goes on the note: `C4'1+E4'3+G4'5`.

**Groups**: braces group notes. Brackets before the braces apply to every note inside, written once (open question 21): `[stacc]{ 12 C4 D4 E4 F4 }`; a note can add its own: `D4[acc]`. A ratio before the braces makes the group a tuplet, with durations inside still in `div` units of actual time: `3:2{ 16 C5 D5 E5 }`, `3:2[acc]{ … }`. Explicit ratios keep tuplets from being rewritten as dotted values.

**Lyrics**, one line per verse under the voice line, one syllable per note in order, grace notes and rests skipped, ABC style: `1.1 L1: Ah vous di- rai- je`. A trailing `-` continues the word, `_` holds the previous syllable over one more note, `*` skips a note.

**Repeated bars** (open question 20): `mN = mK` for a bar identical to bar K in every voice and mark, `s.v = mK` for one voice. K is always a bar written out in full within the same text. No transposed references, relative octaves, repeat groups or pitch shapes (open questions 20, 21). Spelling stays `Bb4` (open question 19).

**In ideas**: a voice line replaces everything in that voice for that bar: notes, rests, decorations, marks and the lines that start or end in it, so the read-back shows exactly what was written. A line that holds only marks, with no durations, notes or rests, changes those marks and leaves the notes alone. A system object is rewritten only through staff 1 voice 1.

**Read but not written** (the plugin API cannot, `research/musescore-4.7.5-element-coverage.md`): glissando, two-chord tremolo and chord lines (`[gliss]`, `[trem2]`, `[fall]` and the like are refused in ideas, with the reason), instrument changes with a real instrument (only the label could be added), fretboard diagram dots and harp pedal states. Bar lines other than repeats and key changes on transposing staves are partial; title and composer are written outside the undo step, so `discard` cannot remove them.

Rules for N1x:

- It lives in Reflets (`reflets/n1x.py`) while it is built, and moves upstream to the engine later if the hosted app wants it (open question 23). It builds on the engine's `Measure` and `Event`; the elements N1 has no field for live in Reflets' own structures.
- A test keeps the two from drifting: N1x with every extension stripped equals `engine.notes.encode` byte for byte on the test scores.
- Slurs that cross another slur in the same voice (the nocturne has five, the Brahms Op. 118 No. 2 export three) are numbered, `(2 … )2`; nested and separate slurs stay `( … )`.

As built in slice 3 (header and bar fields; protocol 3, plugin 0.3.0): `read_score` returns N1x with the header lines and every bar field above, and since protocol 4 the marks; lines, decorations, groups, lyrics and repeated bars followed. `n1x.py` has its own voice loop, a copy of the engine's, so the strip test (`tests/live_read.py`) compares two implementations. `ks=` follows staff 1's key; a range that starts after a key change gets `ks=` on its first bar. `jump=` uses short names for MuseScore's jump table (`dc`, `dc-al-fine`, `dc-al-coda`, `ds-al-coda`, `ds-al-fine`, `ds`, `dc-al-dblcoda`, `ds-al-dblcoda`, `dss`, `dss-al-coda`, `dss-al-dblcoda`, `dss-al-fine`), matched on `jumpTo`, `playUntil` and `continueAt` because the plugin API has no jump type; any other jump is written `jump=<jumpTo>:<playUntil>:<continueAt>`. `mark=` names MuseScore's `MarkerType` (`segno`, `varsegno`, `coda`, `varcoda`, `codetta`, `fine`, `tocoda`, `tocodasym`, `dacoda`, `dadblcoda`, `user`). Not carried yet: the text of a jump or marker where the user changed it, a user marker's text, and bar lines other than the end bar line of staff 1. `bar=` names `double`, `dashed`, `final`, `dotted`, `reverse-final`, `heavy`, `double-heavy`; repeat bar lines come from `rep=`. `break=` adds `nobreak` (keep the bar on the same system). `volta=` takes the endings from `volta_ending`, which reads correctly on voltas loaded from a file, and from the text when it reads back empty, as on a volta created inside a command (spike, 2026-10-19). MuseScore's MusicXML import turns segno, coda, Fine, To Coda and D.S. al Coda into staff text and drops a dashed bar line, so the test score `tests/data/bar-fields.mscz` has them added by hand. `propose` accepts N1x, skips the header lines and refuses bar fields other than `len` and `ts` until slice 4. Marks, as built (protocol 4, plugin 0.4.0): read from `Segment.annotations` and Clef segments, in MuseScore's order within a tick. Dynamics use MuseScore's `DynamicType` names in lower case (`!mf`, `!sfz`, `!fp`); a dynamic of type other is written with its text, `!"…"`. Text is shown without its formatting tags (`<b>`, `<i>`, `<font>`) and entities. Tempo text drops the metronome mark and keeps its words, and the mark's beat unit is not carried (a dotted-quarter 40 reads `q60`). Figured bass writes stacked figures with `/`. Clefs are named `treble`, `treble8vb`, `treble8va`, `alto`, `tenor`, `bass`, `bass8vb`, `perc`, `tab`, and by MuseScore's own name otherwise (`C1`, `F3`). Chord symbols are written as their text whatever their `harmonyType` (standard, Roman, Nashville). A chord symbol in a score imported from MusicXML that has not been saved and reopened reads `""`: MuseScore fills its text only when a file is loaded or the symbol is edited (`Harmony::afterRead`), and the plugin API has no chord name. A mark on a rest that N1 folds into a gap goes before the gap when it starts it, else after the gap with `@`; a mark after the last note takes `@`; a mark in a voice with no notes in that bar gets a voice line of marks only, each with `@`. Fermatas, also segment annotations, come with decorations; instrument changes, fretboard and harp diagrams, sticking, capo, string tunings and triplet feel are not read yet. Test score: `tests/data/marks.mscz`, the import of `marks.musicxml` with the expression, system text, playing technique, the "Dm7" chord symbol and the staff text on staff 2 added by hand. Ideas with marks are refused until slice 4. Decorations, as built (protocol 5, plugin 0.5.0), first step: articulations and ornaments by the short names above, MuseScore's `SymId` name for the rest (`[articStressAbove]`); `arp`, `arp-up`, `arp-down`, `arp-bracket`, `arp-up-straight`, `arp-down-straight`; `trem8` to `trem64` and `buzz`; `fermata` on the note or rest it stands over, and `breath` or `caesura` on the note or rest it follows (`1 r[fermata]`), else as `[fermata]@<offset>` like a mark; `lv`, `paren`; grace types other than the default as `acciacc`, `appog`, `grace4`, `grace16`, `grace32`, `after`, `after16`, `after32`. A decoration of one note in a chord takes a colon on the note (open question 25). Second step: noteheads as `head=` with MuseScore's own names (`head=x` for the cross, `head=diamond`), cross-staff as `staff+1` or `staff-1` on the chord, fingering on the note, `C4'1`. Stem direction and beam mode are not shown, although the plugin sends them: MuseScore's MusicXML import stores an explicit stem or beam mode on almost every chord, the plugin API cannot tell these from a user's choice or give MuseScore's default to compare with, and showing them made the nocturne's N1x 89% longer (13,269 characters against 7,020); left out by default after the owner was asked and had no preference, to revisit with writing in slice 4. Test score: `tests/data/decorations.mscz`, the import of `decorations.musicxml`. When a lower staff also shows system markings (Layout panel), MuseScore returns a copy of each system object for that staff too: tempo, rehearsal marks and system text are placed in staff 1 voice 1 and read once, and identical jumps and markers in one bar are read once (`tests/data/system-marks.mscz`, three instruments with system markings on the violin as well, and a rit. line added by hand). Groups, as built (protocol 6, plugin 0.6.0), third step: every tuplet is written with its ratio and braces, `3:2{ 30 C5 D5 E5 }`, nested ones inside their outer one, `3:2{ 60 C5 D5 3:2{ 20 E5 40 r } }`; rests inside a tuplet are written inside its braces, so a rest that N1 writes as one gap is split where a tuplet starts or ends (`3:2{ 30 C5 60 r } 45 r D5`), and rests at the end of a bar are written when a tuplet ends there. A run of three or more notes or chords with the same decorations (open question 24) gets them once before braces, `[stacc]{ 45 F5 G5 A5 B5 }`; a run does not cross the start or end of a tuplet, and a run that fills a tuplet exactly joins its ratio, `3:2[acc]{ 60 C5 D5 E5 }`. A note with grace notes before it is never in a run. Durations keep N1's rule (a number stands until the next one), braces or not, so the strip test removes the braces and compares both texts after the engine has decoded and re-encoded them, which merges split rests. MuseScore's MusicXML import gets nested tuplets wrong (an outer triplet of a whole note), so the triplet inside bar 5's triplet of the test score `tests/data/groups.mscz` (the import of `groups.musicxml`) was added by hand. Ideas with braces are refused until slice 4. Lines, as built (protocol 7, plugin 0.7.0): the names above, plus `22mb`, `upprall`, `downprall`, `prallprall` for the other trill lines, `vib-wide`, `vib-sawtooth`, `vib-sawtooth-wide`, `tempo"rit."( … tempo)` for a gradual tempo change (rit., accel.) with its text, `whammy(` and `hopo(` (hammer-on and pull-off), and MuseScore's own name in lower case for any other; pedal and octave line texts are not carried. An opener goes before the note or rest it starts on, among the marks there, after the bar's other marks at that tick; a closer goes after the note or rest that ends at its tick, after any closing brace and before the marks and openers of the next note, else after the note it falls in with `@` (`ped)@2`); a line that ends at a bar line closes in the bar before it. At one tick, longer lines open first and close last, and lines with the same start and end nest in a fixed order by name. A slur that ends on a grace note before its main note closes after the grace notes: `( gG4 gBb4 gEb5 ) 24 G5`. A closer is written in the voice line of the line's end track (`spannerTrack2`). Gradual tempo changes and system text lines are system objects, placed in staff 1 voice 1 and read once. A read of a bar range carries the lines that start or end in it; a line that starts before the range shows only its closer, one that ends after it only its opener, and one that covers the whole range is not shown. A glissando is a decoration of the note it starts from, `[gliss]` or `[gliss-wavy]`; note-anchored lines, guitar bends and lyrics lines are not read yet. MuseScore's MusicXML import reads a wavy glissando as wavy, but it reads straight after the score is saved and reopened. Test score: `tests/data/lines.mscz`, the import of `lines.musicxml` with the rit. line and the cresc. line added by hand; vibrato, let ring, palm mute and whammy bar are mapped but not tested live. Ideas with lines are refused until slice 4. Lyrics, as built (protocol 8, plugin 0.8.0): the plugin sends `Y <tick> <track> <verse> <syllabic> <lyricTicks> <text>` after each chord line, from `ChordRest.lyrics` with `plainText`, and for a read that starts after the first bar it first sends, per track, the lyrics of the last chord with lyrics before the range when their melisma reaches into it, so a held syllable reads `_` at the start of the window. That walk back goes bar by bar and runs only when the score has lyrics; it skips parts without lyrics, and stops on a track at its first rest, its last chord with any lyrics, or a bar where it has no chord, so an empty voice costs one bar; a voice with notes but no lyrics in a part with lyrics is walked back to its last rest, which may be far. A verse held across a window start while another verse has a syllable on that last chord reads `*` there. Each verse with a syllable or a held note in the bar gets a line `s.v Ln:` after its voice line; one token per chord, tied continuations included, grace notes and rests skipped, trailing `*` dropped. `-` follows a syllable whose `syllabic` is begin or middle; `_` marks a chord after a syllable whose melisma (`lyricTicks`, measured to the last held chord's start) reaches it; any other chord without a syllable is `*`, so a word hyphenated across a note without its own syllable reads `won- * der`. A syllable is quoted when it is empty, contains a space or `"`, starts with `_` or `*`, or ends with `-` (`"you are"`). Lyrics on rests and grace notes are not read, nor lyric formatting. Test score: `tests/data/lyrics.mscz`, the import of `lyrics.musicxml`, saved; a hyphenated syllable that is also held is not tested. Ideas with lyric lines are refused until slice 4. Repeated bars, as built (no protocol change): written by the server after the bars are encoded, with the rules of the compression study (`research/encoding-tokens/compression/codecs_n1.py`). `mN = mK` when bar N's fields after its number and every line under it, lyric lines included, equal bar K's, K being the first such bar written out with no reference in it, and the reference is shorter than the bar. Otherwise `s.v = mK` replaces a voice line equal to that voice's line in the first bar that wrote it out, when the reference is shorter than the line; lyric lines are never referenced, so a verse with the same tune and new words reads `1.1 = m1` followed by its own `1.1 L1:` line. A read of a bar range refers only to bars inside it, so the first occurrence is written out in each window. On the nocturne references shorten the N1x by 10% (7,449 to 6,722 characters), less than the study's 25% on N1 because marks, lines and decorations make more bars differ. Test score: `tests/data/repeats.mscz`, the import of `repeats.musicxml`, saved; the strip test expands references before comparing with N1. Ideas with references are refused until slice 4. Marks at one moment are written in a fixed order since slice 4's second step: clef, tempo, rehearsal mark, system text, staff text, expression, playing technique, figured bass, dynamic, chord symbol, then line openers, so the same score reads the same after an undo that reorders annotations. Two marks of one kind at one moment are ordered by their value and text (`!fp !z`). Since slice 4's fourth step, lines are numbered where the pairing rule of writing (4.3) would pair them wrongly within the range read: `(2 … )2`, `ped(2 … ped)2`, the number after the parenthesis; crossing slurs in one voice get one, as does a line closed in the range inside a line that closes after it. None of the test scores, the nocturne included, needs a number. As built in slice 4 (bar fields): a final bar line on the last bar is MuseScore's default and is not read as `bar=final`; MuseScore stops reporting it as set by the user once it has been removed and set again. As built in slice 4 (keys): `Staff.key` gives a staff's written key, so a score whose first staff transposes read the clarinet's D major as `ks=2s`; `info` now subtracts from each staff's key the difference between `actualKey` and `concertKey` of the staff's first key signature, and `K` lines carry concert keys.

### 4.3 One grammar for reading and writing

The model writes an idea as an N1x fragment for a bar range and a part. The server decodes it, validates it against the score's meter and part layout, and compiles it to Protocol A ops. A parse error is returned as `ToolError` naming the offending token and bar (`hosts:50`). Using the read format as the write format means the model has seen hundreds of examples of the grammar before it writes, and the tool description does not have to teach a second language. This follows the research conclusion to put verbosity into a compact encoding and a batched write mini-DSL rather than into many tools (`deep:112`).

As built in slice 2: ideas are plain N1 (`engine.notes.decode`), no engine change. Each voice line replaces that voice in that bar; voices and bars not written are untouched; a voice line of rests only empties the voice, and silence at the end of a line becomes rests. Durations that note entry cannot take in one value are split into tied notes; durations needing a tuplet are refused. N1 has no grace type, so a single grace is written as `acciaccatura` and a group as `grace16`; grace chords are refused. A tie needs the next note of that voice, in the idea, back to back on the same pitch. `len=` must equal the score's bar. As built in slice 4, first step: ideas are decoded by Reflets' own N1x decoder (`n1x.decode`), which reads the whole grammar `read_score` writes, header, bar fields, marks, lines, decorations, groups, lyrics and references, into per-voice structures; the engine's N1 decoder is no longer used for ideas. `mN = mK` and `s.v = mK` are expanded first and must point at a bar written out earlier in the idea. Tuplets (`3:2{ … }`, nested too, with rests inside) and grace chords are written; a tuplet may not cross the bar line, nor a note or rest the edge of a tuplet. Bar fields are accepted when they equal what the score has (so a bar copied from `read_score` can be sent back) and refused when they would change it; `title=` and `composer=` likewise (open question 29). Marks, lines, decorations, groups with decorations and lyrics are still refused; the marks and lines already in a voice stay when its notes are replaced, so the replace part of the 4.2 rule comes with each family's step. Second step: marks are written. A voice line replaces that voice's marks in its bar as well as its notes (4.2), so replacing a voice removes its dynamics, chord symbols and texts, and in 1.1 also the tempo, rehearsal marks and system text; a voice line with only marks (no duration, note or rest) replaces the voice's marks and leaves its notes, and does not need `replace=True`. `!name` takes MuseScore's `DynamicType` names, `!"…"` an other-type dynamic with that text; `q90` without words gets the metronome mark as its text, read back as `q90`; `clef=` takes the names `read_score` writes. Tempo, rehearsal marks and system text are refused outside 1.1 and clefs outside voice 1. Playing technique is written as text only: its `playTechType` stays the default, so `pt"pizz."` shows but may not change playback. A mark needs a note or rest at its tick in some track; MuseScore's mid-note time-tick segments are not created. Fermatas, lines and lyrics stay as they are. Third step: decorations are written, with the names `read_score` uses or MuseScore's own `SymId` name, on chords, single notes (`C4:paren+E4`), rests (`fermata` and `breath` only) and grace notes (their type only, and fingering); `[gliss]` and the other kinds 4.2 lists as read only are refused with the reason. On a note split into tied notes, decorations go on the first and `lv` and a breath on the last. A rest is split where a mark falls inside it, so the mark has a rest to stand on. A tie may end in the bar after the idea when that bar is not part of the idea, as in reading. Lines that start or end on a rewritten voice's grace notes or tuplets are removed with them, and lyrics with the notes, until those families are written. `tests/live_roundtrip.py` writes every bar of the open score back as `read_score` returns it, lines and lyrics left out, and checks the read-back and the discard; it passes on the nocturne and the eight test scores, the glissando bar of `lines.mscz` being refused. Fourth step: lines are written (open questions 27 and 30). A voice line replaces the lines that start or end in it, like its other marks: the plugin removes those and writes the idea's. Openers and closers pair by name and number within one track in the order of the text, bars in score order, then a closer left over pairs with the latest opener of the same name in another track (a cross-staff slur). An opener with no closer in the idea is refused. A closer with no opener ends the line from before the idea that ended in that voice within the idea's bars, keeping its start, kind and text; a closer with neither is refused. An idea that leaves out one end of a line crossing its edge is refused (open question 31): a closer for a line from before the idea, or an opener for a line ending after it, unless the idea closes that line inside itself. `tempo"…"(` is refused outside 1.1. Text lines are written as staff text lines, so a system text line read in 1.1 comes back as a staff one; a gradual tempo change gets only its text, its tempo change type staying MuseScore's default. `hopo(` and names `read_score` does not use are refused. Slurs are anchored to notes, so slurs on grace notes and tuplets are written now; rests are no longer split at a line's opener or closer. Not tested: an octave line added over notes the idea does not write changes their sound, which the read-back should catch as a change outside the written voices and undo. `tests/live_roundtrip.py` now writes, from each bar, the shortest range whose lines all close in it, lines included and lyrics and glissandos left out, and passes on the nocturne and the eight test scores; `tests/live_write.py` also checks both refusals and re-ends a slur from bar 4 in bar 5. Keeping details, first stage (decisions 32, 33 and 35): `propose` reads the bars before compiling. A voice line's marks are matched with the bar and voice's existing marks by token, the nearest moment first: a token the cell already has refers to that mark wherever the idea puts it, so a mark written as read stays where it was after a change of rhythm and is never doubled; other tokens are added, and a token with a leading minus removes the cell's mark with that token nearest its moment, or is refused when there is none. Fermatas and breaths, on notes, rests or with `@`, are matched the same way. A new chord keeps the chord-level decorations of the old chord at its moment, and each new note the note-level ones (fingering, parentheses, notehead, let ring) of the old note of the same spelling; `[-name]` and `C4:-name` remove them. A note whose old chord has a glissando or another decoration the plugin cannot create is refused unless the idea removes it (`[-gliss]`). System marks reported again for a lower staff that shows system markings are matched once, and a mark at the very end of a bar is left alone, as in reading. Lines keep the replace rule until the second stage. Keeping details, second stage (decisions 32 to 34): lines stay as they are. A line token the bar and voice already have (an opener where a line starts in that cell, a closer where one ends) refers to that line, the nearest first, opener and closer separately; the remaining tokens pair into new lines as in reading, and a new line needs both ends in the idea. `-name(` or `-name)` removes the line with that end; a new closer left unpaired after such a removal takes the removed line's start (a move, `-ped) ped)@96`), a new opener its end; any other unpaired token is refused, a closer with the hint to remove the old end. Every slur that starts or ends in a voice whose notes are rewritten is removed and written again on the notes sounding at its old start and end (its start on the chord sounding there or the nearest, its end at the end of the chord sounding just before it or the nearest; an end on grace notes that are still there stays), refused when it would fall on one note without grace notes before it; other lines are left to MuseScore, which keeps them. A slur written again takes the idea's colour. Superseded: the refusals of decisions 27, 30 and 31. Lyrics (decisions 36 and 37): a lyric line sets its verse in its voice and bar, one syllable per note in order (rests and grace notes skipped, more syllables than notes refused), from a timed voice line's notes or, under a marks-only line (an empty `1.1:` will do), the bar's notes as read; `_` extends the syllable before it, from an earlier bar too, and a bar that starts without `_` ends a hold reaching into it; the last syllable keeps a hold the old one at its moment had past the bar. A voice whose notes are rewritten keeps its other verses by moment; a syllable left without a note is removed and named in the result. The read-back compares every written voice's lyrics, held notes included. A syllable starting with `-` needs no quotes, since a lyric line has no minus tokens (decision 33 expected quotes). A tie from the bar before into a voice whose notes are rewritten, that bar's voice not rewritten too, was cut silently, since note entry removes it and the read-back covered only the idea's bars; now it is tied again when the voice still starts with that pitch, checked in the read-back, and otherwise named in the result as cut. Bar fields (decision 38): `rep=` and `bar=` take the value written, `x=` needs a repeat end, `break=`, `jump=` and `mark=` add the values missing, and a minus removes a value the bar has, else the idea is refused. A `volta=` on bars with none adds one volta per run of consecutive bars with the same endings; on a bar under another volta it is refused until the idea removes that one, and `-volta=` removes the whole volta, bars outside the idea included. New jumps take MuseScore's usual text ("D.S. al Coda"); markers get their text from `markerType`. An idea may consist of bar lines only. After the write the server reads `info` again and compares each idea bar's fields, and the bar ticks, with the expected ones. `ts=` and `ks=` are still refused. Meters (decision 39): `ts=` changes the meter from that bar to the next meter change, `-ts=` (or `ts=` with the meter before) removes the bar's meter change. Of another length, the bar must stand alone in the idea, as the idea's last bar with no voice lines, and the bars it re-bars, up to the next meter change, must have no notes and no lines (marks on rests stay at their moment); the read-back then checks only the bar's meter, since markers and the like move with the re-barring, and not the notes. For a meter of the same length the server reads the bars up to the next meter change before and after and refuses the idea, undoing it, when anything after the idea's bars changed. Keys (decision 40): `ks=` sets the concert key from that bar to the next key change, `-ks=` (or `ks=` with the key before) removes the bar's key change; notes keep their pitches and spelling. The read-back compares the bar's key. Recasts (decision 41): with `recast=True`, an idea whose first bar has `ts=` of another length rewrites that bar and the bars after it, bar for bar, in the new meter, up to the idea's end or a later bar of the idea that writes `ts=` with its own meter, after which the old meter goes on; that bar is written as usual, its marks staying where they are. It must write every voice that has notes, rests or marks in those bars. In one write the plugin removes their marks and lines, puts a time signature with the old meter on the bar after them, fills their voices with rests, sets each bar's actual length to the new one (`timesigActual`, which calls `adjustToLen`) and adds the new time signature on the first, so MuseScore, which re-bars a span into as many bars as its length needs, keeps one bar per bar in either direction; then the idea is compiled against the bar layout that results, with the old marks, lines, syllables and decorations moved to the same fraction of the bar (marks and line ends onto the nearest note or rest the idea starts there) and kept by the usual rules, and written back. The read-back is the full one, against that layout, and the bars after the recast up to the next meter change are compared with their ticks shifted. A time signature change alone splits a bar going into a shorter meter (6 quarter notes into two 4/4 bars), and removing the extra bars with `time-delete` from the plugin crashed MuseScore 4.7.5, while `delete` and `full-measure-rest` did nothing; hence the actual-length step. The tempo stays as written; the idea writes the new one. `tests/live_recast.py` checks 4/4 to 12/8 and 4/4 to 3/4 on `tests/data/recast.musicxml`, and `tests/live_write.py` 12/8 to 4/4 on the nocturne's first bar.

### 4.4 Read windows and the token budget

- Claude Code warns at 10,000 tokens of MCP output and caps at 25,000 by default (`hosts:41`); results over 50,000 characters are written to a file instead (`plan:69`).
- Measured density: about 1,700 tokens for 38 bars of dense two-hand piano (`plan:54`), so roughly 45 tokens per bar at that texture. The server estimates tokens as characters / 3.5 (`plan:56`), returns the whole score when the estimate is under 6,000 tokens, and otherwise returns the first 16 bars with a one-line notice of the total. A request estimated over 18,000 tokens is refused with a suggestion to narrow the bar or part range. Real counts are measured with the token-count API during implementation (`plan:56`, `deep:121`).
- `read_score(since=<fp>)` returns only bars whose fingerprint changed since the last read, for the "check what I've written so far" loop (`notes:185`).

### 4.5 Positions

Bars and beats in model-facing text follow the engine's `Finding(bars, beats, ...)` and `Position`/`NoteRef` conventions (`engine:85`, `engine:23`), with a pickup numbered 0 (`engine:7`). Bar numbers must equal what the user sees in MuseScore; the server computes them from `Measure.no`, `noOffset` and `irregular` (`api:66`). **[spike]** verify against the on-screen numbers with and without a pickup.

## 5. MCP tools

Constraints from the research: fewer than ten compact tools, three to five marked always loaded, since Claude Code defers all MCP tool schemas behind tool search by default (`deep:112`, `hosts:42`); upfront descriptions and server instructions are cut at 4,096 characters, deferred descriptions at 16,384 (`hosts:42`); tool names over 128 characters are dropped (`hosts:45`); 58 tools cost about 55,000 tokens before the first message, which is the failure mode to avoid (`deep:105`).

### 5.1 The eight tools

| Tool | Always loaded | Read-only | Purpose |
|---|---|---|---|
| `score_info` | yes | yes | Connection state, MuseScore version, title, parts with staves, bar count, meter and key, current fingerprint. Also the health check. |
| `read_score` | yes | yes | N1x for a bar range and optional part filter; `since=` for changed bars only. |
| `check` | yes | yes | Rule-based critic on a bar range: the ten voice-leading rules (`engine:79`) and the beat-by-beat notes table (`engine:18`), as text. |
| `propose` | yes | no | Write an N1x idea into the score, in place as one undo step or as a new tab (section 7). Returns the read-back summary and a proposal id. |
| `discard` | no | no | Undo the last Reflets proposal if the score has not changed since (6.9). |
| `render` | no | yes | Engrave a bar range to PNG through the engine, with optional annotations (`engine:24-25`). Needs `export` (section 7.3). |
| `analyze` | no | yes | Notes table and, when the optional model environment is installed, the harmony draft (`engine:22`, `engine:57`). |
| `doctor` | no | yes | Diagnostics: plugin file present in the plugin folder (`api:113`), port reachable, MuseScore version, WebSocket API present (`deep:17`), engine extras installed. |

Four always loaded, within the three-to-five guidance (`deep:112`). `_meta["anthropic/alwaysLoad"]: true` on those four (`hosts:42`). Tool annotations set `readOnlyHint` on the read tools so Codex's `writes` approval mode prompts only for `propose` and `discard` (`hosts:10`). `anthropic/requiresUserInteraction` is not set on any tool, since it forces a prompt on every call (`hosts:43`).

Results are plain text, not `structuredContent`, because structured output is validated against a schema and costs tokens for keys (`hosts:50`); the N1x text is the structure. Errors the model should act on are raised as `ToolError` (`hosts:50`).

### 5.2 Tool contracts

**`score_info()`** → one short paragraph:

```
MuseScore 4.7.5, Reflets bridge 0.1, connected.
"Nocturne in E flat" — 2 parts: P1 Piano (staves 1-2). 38 bars, 12/8, E flat major, pickup: no. fp=3f9a.
```
When not connected, the same text explains what to do and the other tools are not needed.

**`read_score(bars="1-8", parts="P1", since=None)`** → N1x. Defaults as in 4.4.

**`check(bars="1-8", parts=None, rules="voice-leading")`** → the engine's `part_writing.as_text` findings grouped into numbered spots with bar and beat (`engine:85`), preceded by the notes table for the range (`engine:18`). The voice-leading checker applies only to two to four single-line voices with at least 60% shared onsets (`engine:81`); when it does not apply, the tool says so in one line rather than returning silence. Requires the `[checks]` extra (music21, `engine:153`); without it the tool returns the notes table and a one-line install hint. As built (2026-10-21): `check(bars="all")` only, like `read_score`; there is one rule set, and music21 is always installed (11.7), so there is no hint. The range alone is read, so motion into or out of it is not checked. Findings are listed one per line as bar and beat, voices as `staff.voice` and the engine's reason, not through `part_writing.as_text`, whose text is written for the hosted app's annotation step. Live test: `tests/live_check.py`, run with `tests/data/part_writing_motion.musicxml` (the engine's planted errors), `tests/data/bwv66.6.musicxml` (a pickup) and a score the rules do not fit.

**`propose(idea, mode="in_place", label="idea 1", replace=False)`** → text:

```
Written: bars 5-8, P2, 23 notes, 2 rests, 1 tie, as one undo step "Reflets: idea 1". Read-back matched.
Press Play in MuseScore. Call discard("p3") to remove it, or keep working.
proposal id: p3
```
`idea` is N1x for the target bars and parts. `mode="new_tab"` follows 7.3. `replace=True` is required when the target cells are not rests (6.4).

**`discard(proposal_id)`** → confirms the undo, or refuses with the reason (6.9).

**`keep(proposal_id)`** → turns the idea's notes black as their own undo step, `Reflets: keep <label>`, and closes the proposal (7.1). Added in slice 2, owner decision 2026-10-18; nine tools in all. As built, `propose`, `read_score`, `score_info` and (since 2026-10-21) `check` are always loaded; `discard`, `keep`, `analyze`, `render`, `doctor`, `checkpoint`, `checkpoints` and `restore` are deferred: twelve tools, above the fewer-than-ten guidance, but the extra ones are deferred and cost nothing until searched (6.13).

**`render(bars, parts=None, annotations=None)`** → path to a PNG the harness can open, plus one line of text. Large outputs go to a file anyway (`plan:69`). As built (2026-10-21): `render(bars, check=False)`, deferred (11.42). The plugin exports the score as it is, unsaved edits and ideas included, to a file next to the token file, which the server reads and deletes; the engine engraves the range (at most 32 bars, `annotate.MAX_BARS`). With `check=True`, the engine's `part_writing.as_text` spots become callouts and voice-leading marks, drawn in red and listed in the result with the same numbers. PNGs go to the system temp folder under `reflets/`. Live test: `tests/live_render.py`, with the same scores as `check`.

**`analyze(bars)`** → notes table and harmony draft text (`engine:57`). As built (2026-10-21): deferred; the whole score is read and given to the model for context, and the draft is printed for the range. It needs no export: `draft.draft` encodes the index as N1 for the model. The model's environment and checkpoint are named by `ANALYSISGNN_PYTHON` and `ANALYSISGNN_CHECKPOINT`; without them, or when the model fails, the result is the notes table and the reason. The model runs in a thread, as do the check and the engraving, so the bridge's connection is not held up. Live test: `tests/live_analyze.py`.

**`doctor()`** → a checklist with pass or fail per line. As built (2026-10-20): deferred and read-only. It checks, in order: the plugin file next to the token file (`REFLETS_TOKEN_FILE`), and that its `proto` matches the server's; the token file; that something accepts a TCP connection on the port; that it answers `hello` and `info` as the bridge (a server that does not answer is named as another plugin holding the WebSocket server, 3.1); then the bridge's version and protocol, MuseScore's version and the open score. It stops at the first unreachable step. A missing WebSocket API cannot be told apart from a plugin that was not run, since both leave the port closed, so that line names both. Since 2026-10-21 it also names the AnalysisGNN model, as a NOTE rather than a FAIL when it is missing, since `analyze` works without it; music21 and Verovio are required dependencies, so they are not checked. Live test: `tests/live_doctor.py`.

## 6. Write path

### 6.1 Preconditions, checked in the server

- Connected and a score open (`api:11`).
- The target bar range exists. Bars beyond the end can only be appended, never inserted (`api:33`, `api:132`); `propose` appends when the idea runs past the last bar and says so in its result.
- The target tracks exist in `info` (`api:70`).
- The idea's durations fill each bar exactly under the bar's actual meter (`api:66`), with tuplets that do not cross a bar line (`api:49` rejects cross-measure tuplets).
- Every tick the plugin will rewind to lies inside the score: `rewindToTick` has no null check on the segment it finds (`src:34`, `src:61`).

### 6.2 Snapshot

Before writing, the server `read`s the full tick range across all tracks. This pre-snapshot serves the read-back comparison (6.6) and `discard` (6.9).

### 6.3 One undo step

```
score.startCmd("Reflets: <label>")       api:31
  ... ops ...
  ... read back ...
score.endCmd(false)   on match           api:31
score.endCmd(true)    on any failure     api:31  (rollback)
```

`startCmd` locks the undo stack so every change, including those made through `cmd()`, commits as a single command, and `endCmd(true)` rolls back (`api:31`). This is what makes "discard = one Ctrl+Z" true for layout B (`notes:146`).

Commands dispatched inside the lock that open their own `startCmd`/`endCmd`, such as the tie toggle, add nothing at that level because both calls return at once while the stack is locked (`src:65`), so the whole write stays one macro. `endCmd` also forces a rollback when an engraving error is set (`src:67`).

### 6.4 Placing notes and rests

Per `v` pass (one voice, one bar):

1. `cursor = score.newCursor()` (`api:39`). Leave `inputStateMode` at `INPUT_STATE_INDEPENDENT`, the default (`api:46`); in that mode the cursor has its own input state (`src:37`). `INPUT_STATE_SYNC_WITH_SCORE` plus `staffIdx` was reported to write to the wrong staff because it shares the GUI's live input state (`deep:81`, **[reported]**); the research's recommendation is independent mode with an explicit track (`deep:89`).
2. Land: `cursor.track = <staff> * 4` (voice 1 of the target staff), then `cursor.rewindToTick(<barTick>)` (`api:45`). `rewindToTick` moves on to the first segment that has an element in the cursor's track (`src:34-35`), and voice 1 always has a chord or rest at the bar's first segment, so the cursor is now on the bar start. Then `cursor.track = <track>`, which changes the track without moving the segment (`src:36`); if that voice is empty, note entry fills it with rests (`src:51`, `src:57`).
3. For each entry: `cursor.setDuration(z, n)` on a `d` line (`api:49`; an invalid duration silently becomes a quarter, `src:33`, so the server validates first); `cursor.addNote(pitch)` for the first note of an `n` line and `cursor.addNote(pitch, true)` for each further chord member, which joins the chord just written (`src:42`, `src:60`); `cursor.addRest()` for `r` (`api:49`). After each `addNote` or `addRest` the cursor's own input state advances to the next input position (`src:43-44`), so the next entry lands after it.
4. `t`: `cursor.addTuplet(ratio, duration)` (`api:49`) at the current position, then its `n` and `r` entries; cross-measure tuplets are rejected (`api:49`).

Spelling pass, after all voice passes: for each chord written, find its segment by tick (`findSegmentAtTick`, `api:33`), take `elementAt(track)` (`api:65`), its `notes` (`api:63`), and set `tpc1` and `tpc2` (`api:60`, writable). `cursor.element` cannot be used for this: after `addNote` the cursor already sits on the next position (`src:43`, `src:59`).

Existing content: `addNote` overwrites. Note entry carves a gap of the requested duration out of whatever the voice holds and never inserts time (`src:48`). A duration longer than the remaining bar spills into the next bar with an automatic tie (`src:50`), which is why 6.1 requires exact bar fills. Policy: `propose` requires `replace=True` when the pre-snapshot shows anything but rests in the target cells; the read-back (6.6) checks the result either way.

Grace notes are written in v1 (decided 2026-10-18, spike round 5, `research/spike-bridge-hello-2026-10-18.md`): there is no cursor entry for them (`api:49`), so per `g` op, after all voice passes and the spelling pass, the plugin selects the main chord's first note, dispatches the grace action, and sets `pitch`, `tpc1`, `tpc2` on the new grace note, which MuseScore creates at the main note's pitch. New graces before a note are inserted at the front of `graceNotes`, so the server emits a note's before-graces in reverse order. Like ties, this needs the dialog-free plugin (2.1).

### 6.5 Ties

There is no API to create a tie: `Cursor::add` has no TIE case, `tieBack`/`tieForward` are read-only, and `newElement(TIE)` plus `cursor.add` crashed MuseScore 4.6.5 (`deep:70`). The only path is `cmd("tie")` over a selection, which toggles (`deep:70`). Procedure per `~` op, after all notes exist:

1. The server emits `~` only when it has written both the note and a same-pitch successor in the same part and staff, since that is what `searchTieNote` looks for (`src:76`), and because 4.7.5 falls back to adding a brand-new tied note when a lone selected note has no successor (`src:74`).
2. Find the note at (track, tick, pitch) from a fresh read; `selection.select(note)` (`api:80`; the call is refused if the selection is locked or the element type cannot be recorded, both reported as `write-failed`). A single selected note gives the tie command exactly that note (`src:72`).
3. Read `note.tieForward` (`api:60`). If already set, skip the command: the toggle would remove it (`deep:70`, `src:73`).
4. `cmd("tie")` (`api:17`); the code is `tie` on 4.4.4, 4.6.2 and 4.7.5 (`src:15`). Confirmed on 4.7.5 inside `startCmd`, one undo step with the notes, **only when no plugin dialog is open** (2.1, `research/spike-bridge-hello-2026-10-18.md`). The command's own `startCmd`/`endCmd` are no-ops under the plugin's lock (`src:65`), so the tie stays inside the one undo step; the same core logic exists on 4.4.4 (`src:75`).
5. Re-read `tieForward`. If still null, `verify-failed` → rollback. Direct Tie creation is never attempted (`deep:77`).

Selection inside an active command: `select(e)` has no undo-stack guard, only the lock and type checks (`api:80`, `api:84`); the claim that `selectRange` is refused inside `startCmd` was refuted 0-3 (`deep:175`). `selectRange` inside a command is applied deferred by tick (`api:81`), which is why ties use `select(note)`, not `selectRange`.

### 6.6 Read-back verification, inside the command

After the ops, the plugin re-walks `[startTick, endTick)` on **all** tracks, not just the target (`deep:89`: a target-only read-back can confirm a wrong write). The server compares against the expected state: pre-snapshot with the target tracks' cells replaced by the idea. Any difference, including on a non-target track, is `verify-failed`, and the plugin calls `endCmd(true)`. This is the only correctness signal available, because `cmd()` dispatches any string unmapped and an unknown action is a silent no-op (`api:17`, `deep:66`, `plan:64`), `setDuration` silently substitutes a quarter (`api:49`), and `addNote` may land on the wrong staff (`deep:81`).

The read-back is of the score model, not the layout, so `doLayout` (`api:32`) is not required for it; `endCmd` notifies the notation of the change (`api:31`). **[spike]** confirm that annotations added with `undoAddElement` are visible to `Segment.annotations` before `endCmd`.

As built in slice 2: the plugin commits with `endCmd(false)` and returns the read-back; the server compares it with the expected state and, on a mismatch, sends `undo` and checks the range is back to the pre-snapshot. Comparing inside the command would need the expected state in the plugin, against 2.3; the undo path is the one `discard` already depends on. Compared per (bar, track): pitch, concert tpc, written duration, tie flags, grace type and order, and every `A` line. One expected difference is allowed: a tie running into or out of the idea from a bar outside it is cut, because its note was replaced; the result says so. A plugin exception rolls back with `endCmd(true)` and returns `write-failed <op> <why>`. As built in slice 4, first step (open question 26): the voices the idea writes are checked through N1x: the read-back is encoded with `n1x.encode`, decoded again with `n1x.decode`, and each written voice is compared with the idea's decoded voice: chords with onset, duration, notes, ties, decorations and grace chords, tuplets, lyrics and decorated rests. A chord tied in full to the next chord with the same notes counts as one chord, since a duration that needs two values is written as tied notes. Rests are compared only where they carry a decoration, and marks and lines not yet, as ideas cannot write them. Voices outside the idea keep the raw per-cell comparison with the tie-cut allowance, and the `A` lines must stay the same. A mismatch names the bar and voice with the line as written and as read back. Second step: the written voices' marks, apart from lines and bracketed fermatas, are part of the comparison, as a set of (moment, token); a marks-only line is compared on its marks alone, and its notes by the raw comparison of cells outside the idea. The `A` and `F` lines of voices outside the idea must stay the same, system marks counting as 1.1's. Reads are compared as sorted line lists in `propose` and `discard`, since undo restores a segment's annotations in reverse order. Third step: chord and note decorations and fingering are compared with the chords; a rest's decorations and a bracketed mark (`[fermata]@24`, as a fermata on a rest after a voice's last note reads) are compared as marks at their moment, a breath at the end of its rest. A chord tied in full to the next counts as one with both chords' decorations. Lyrics are left out of the comparison until they can be written, since a syllable held from before the idea still reads `_` on its first note. Fourth step: lines are compared as spans, not as tokens. Every spanner in the reads before and after (the plugin's `N` lines, system lines counted as 1.1's and their copies once) that starts or ends in a written voice must be one of the idea's lines, each taken as start tick and track, end tick and track, whether it ends on a grace note, name and text; the spanners that do not must be the same before and after. Keeping details, first stage: each written voice is compared with the expected result, the idea merged with what the bar and voice kept, not with the idea text; fermatas and breaths are compared as marks at their moment wherever they stand, and a single note's parentheses, notehead and let ring as the note's own. `tests/live_roundtrip.py` writes each range three times, as read (no change), with a minus on every mark and decoration (all must go) and as read again (all must come back). Second stage: all the lines in the bars read are compared with the expected set, the lines before the write without those removed, plus the new, moved and re-hung ones.

### 6.7 Annotations

Per `a` op: `newElement(type)` (`api:18`), position the cursor (6.4 steps 1 to 2), `cursor.add(el)`, which routes Harmony, Dynamic and StaffText through the default `undoAddElement` path (`api:50`), then set `text`, `dynamicType` or `harmonyType` (`api:59`). Dynamics need both, text first: `dynamicType` alone gives the right type and velocity but empty, invisible text; `text` alone shows "mf" but leaves `dynamicType` at 0 (OTHER) (spike, `research/spike-bridge-hello-2026-10-18.md`). Chord symbol text set after `cursor.add` did not crash on 4.7.5. Text is set **after** insertion because chord symbols crashed when text was set before (`notes:169`, **[reported]**). Verified by the `A` lines in the read-back.

### 6.8 Version-branched action codes

The table lives in the plugin, selected by `mscoreVersion` (`api:21`) at hello, and is echoed to the server so unknown versions are refused up front.

| Action | 40402 to 40699 | 40700 and up | Source |
|---|---|---|---|
| undo | `undo` | `action://notation/undo` | renamed in 4.7; plain `undo` is a silent no-op there (`deep:60`, `src:13`); mcp-score branches by version (`deep:60`) |
| redo | `redo` | `action://notation/redo` | same rename (`src:14`) |
| tie | `tie` | `tie` | unchanged at all three tags (`src:15`, `src:23`) |
| append-measures | `append-measures` | same | unchanged (`src:18`); used by 6.11 if `appendMeasures` ever needs the action path |
| file-export | `file-export` | same | unchanged (`src:20`); fallback route if `writeScore` fails (7.3) |
| play, stop | `play`, `stop` | same | unchanged (`src:19`); not used by the core, reserved for the playback-check idea |

With the 4.7 floor (2.5) only the right column is used; the left stays as a record of why older versions are refused. Only undo and redo need the branch; everything else the core dispatches is stable from 4.4.4 to 4.7.5 (`src:25`). Every `cmd()` is still followed by a read-back (6.6), so a wrong code fails loudly instead of silently.

### 6.9 Discard

`discard(p)`:

1. Re-read the proposal's range. If it differs from the post-write read-back stored with `p`, the user has edited since; refuse, and tell the user to use Ctrl+Z themselves. Undo would otherwise remove their edit.
2. `undo` verb → `cmd(UNDO)` with the version code (6.8), outside any `startCmd`.
3. Read back; it must equal the pre-snapshot, else report a mismatch and stop (the code may have been a silent no-op, `deep:60`).

As built in slice 2: when step 3 fails, the last undo step was something else, such as an edit the user made elsewhere in the score after the idea; the server sends `redo` to put it back, checks the range equals the post-write state again, and tells the model the user can remove the idea with Edit > Undo. Tested live: an idea in bar 10 written after an idea in bars 5-6 survives a discard of the older one.

### 6.10 Highlighting

After `endCmd`, `select <startTick> <endTick> <startStaff> <endStaff>` runs `selectRange` (`api:81`) so the user sees where the idea landed. Done after the command, since inside one it is deferred (`api:81`). Not part of correctness.

### 6.11 Appending bars

When the idea extends past the last bar, `appendMeasures(n)` (`api:33`) runs inside the same command so the append is part of the one undo step.

### 6.12 Not written in v1

Superseded 2026-10-19 by open question 17: everything in 4.2 is written in v1 except the kinds listed there as read only. ### 6.13 Checkpoints and restore (first release, parts 1 and 2 built)

Decided 2026-10-18 (open question 16). MuseScore's undo history is linear, interleaves the user's edits with ideas, and is lost when the score closes, so it cannot take the user back to a chosen state after many rounds. Three parts:

1. **Checkpoint files.** The server asks the plugin to `export` the whole score (`writeScore`, confirmed on 4.7.5: 32 ms, no dialog, spike round 4) to a checkpoint file. Nothing is lost across sessions. Going back to a whole checkpoint means the user opens that file: the plugin cannot replace the open score (`readScore` refuted, 7.2).
2. **Restore bars from a checkpoint.** The server reads the checkpoint, compares it bar by bar with the current score, and writes the chosen bars back through the write path (section 6) as one undo step verified by read-back. Bars outside the request keep the user's later edits. It restores only what the write path can write; the checkpoint file covers the rest.
3. **Proposals and checkpoints persist on disk** next to the score, so a restart of the harness does not lose open ideas.

Decided 2026-10-21 (open question 44): both, named checkpoints on request and an automatic one at each `keep`. Comes after `check`, because restore is only as faithful as the write path (slice 3). As built (2026-10-21), part 1: `checkpoint(name)` saves one and `keep` saves one named `keep <label>` after recolouring (a failure is named in keep's result, the keep stands); `checkpoints()` lists them by number, name and time. The plugin API has no score path (`Score` exposes only `scoreName`) and `writeScore` cannot write .mscz in 4.7.5 (`MscNotationWriter::writeList` is not supported), so each checkpoint is a MusicXML export in `checkpoints/<title>/` in the plugin folder, `NNN <name>.musicxml`, with `NNN <name>.json` holding the name, the time and the bridge's `info` and `read` lines for the whole score, from which restore encodes the checkpoint's bars as N1x. A checkpoint holds whatever the score has, open ideas in blue included. Part 2: `restore(checkpoint, bars)` encodes the checkpoint's bars and the current ones from whole-score indexes (so both get the same `div`), refuses a bar whose length changed since (naming the checkpoint's file), and writes as two proposals merged into one, so `keep` and `discard` act on both: first the current bars with a minus on every mark, decoration, bar field and line closing in the range that the checkpoint does not have at the same moment, and every lyric verse emptied (the round-trip test's bare idea, now `reflets/restore.py`); then the checkpoint's bars as read, with a rest line for a voice it does not have. Two undo steps, not one: since decisions 32-35 a write keeps what it does not name, so clearing and writing in one idea would need a diff of every detail; the bare idea is already proven on every bar of the test scores. Marks the checkpoint has at the same moment are left untouched, since writing them again loses what N1x does not carry (a tempo's "♩ = 120" text). Notes are rewritten, so stem directions and beam modes set by an import go back to MuseScore's defaults, as with any idea. Glissandos are left out and named, the checkpoint file holding them. Part 3, proposals kept on disk, is not built.

### 7.1 In place (layout B)

UX additions decided with B: the idea's notes are coloured (writable `color`, in the same undo step) and set back to black on keep, in addition to the selection of 6.10; `discard` goes through Reflets, which refuses when the bars changed since the write (6.9), so a user edit made after the idea is never undone by mistake; "next idea" is a discard plus a new write.

`propose(mode="in_place")` → section 6 → the user presses Play (there is no playback API, `api:109`; the notes already assume the user presses play, `notes:184`) → keep by doing nothing, or `discard` (6.9), which is the one Ctrl+Z (`notes:146`).

### 7.2 New tab (layout C) with readScore and writeScore on a temporary file (dropped, kept as a record)

1. **Export the current score**: `export musicxml <tmp>/reflets-<uuid>.musicxml` → `writeScore(curScore, path, "musicxml")` (`api:14`; `musicxml` is a registered writer, `api:122`). The path is unique per call because the export goes through the export scenario, which may show overwrite dialogs (`api:14`). **[spike]** The 4.7.5 source implements it for the current score (`api:13-14`), but the handbook said readScore and writeScore were not functional in MuseScore 4 (`deep:38`), and the research asks for a prototype before depending on it (`deep:45`).
2. **Splice in the server**: parse the MusicXML with the standard library, replace the target part's bars with the idea, keep the other parts for context, optionally trim to the idea's bars plus two on each side, and write `<tmp>/reflets-idea-<uuid>.musicxml`. The engine's `ScoreIndex` is not needed for the splice; it is used afterwards to validate the result (`engine:9`).
3. **Open as a new tab**: `open <path>` → `readScore(path)` opens a real project in a new tab (`api:13`). Non-interactive open is not available (`api:13`, `api:129`). **Refuted on 4.7.5** (spike round 4, `research/spike-bridge-hello-2026-10-18.md`): with a score already open, `readScore` starts a second MuseScore process with the file and returns the old score; the bridge cannot see the new window. It loads into the bridge's window only when no score is open. **Layout C as written does not work; needs a redesign before implementation.**
4. **The idea tab is now the current score.** Every later `read`, `info` and `write` targets it, because the API only sees the current score (`api:11`, `api:127`). The server tracks this: `hello`/`info` return the title and fingerprint, and `score_info` says "current tab is the idea score" until the user switches back. `propose` refuses to write while the current score is an idea tab.
5. **Approve**: the user switches back to their score and the model calls `propose(mode="in_place")` with the same idea. **Discard**: the user closes the idea tab; the plugin can only close the current score (`api:15`, `api:130`), so the server never closes tabs on the user's behalf.

File paths across WSL2 and Windows: mirrored networking shares `127.0.0.1` (`plan:37`, `rig:27`) but not paths. The server setting `REFLETS_TMP` names a directory both sides can read; when the server runs in WSL and MuseScore on Windows it is under `/mnt/c/...` and the path sent in `open` is translated to Windows form. `readScore` reads any path (`api:13`); `writeScore` goes through the export scenario rather than the `FileIO` path guard (`api:14`, `api:20`). **[spike]** whether the export scenario restricts the destination.

### 7.3 Shared with render and analyze

`render` and `analyze` use the same `export` step because engraving and annotation need MusicXML bytes (`engine:24-25`, `engine:59`). If `writeScore` turns out not to work on some version, the fallback is to ask the user to save and run the MuseScore command line on the saved file (`rig:34`); no plugin can be run from the command line (`api:120`, `rig:19`), so the fallback only sees the last saved state. As built (2026-10-21): only `render` exports; `analyze` works from the read. The export goes next to the token file, which both sides can reach, rather than to `REFLETS_TMP`, which is not built; from WSL its path is sent in Windows form.

## 8. Server internals

- Package `reflets` with a `reflets-server` console script; stdio transport; `MCPServer` from `mcp>=2.3` (`hosts:50`). Logging to stderr only (`hosts:52`; the SDK diverts stray stdout, `hosts:50`).
- Startup under one second, no network at import time (`hosts:19`).
- Connection manager as in 3.3 and 3.4, one request in flight, request ids per connection.
- Cache: raw `M`/`C`/`R`/`A` lines per measure keyed by fingerprint; `info` refreshed on each `fp` mismatch of the part or measure tables.
- Engine dependency tiers: core (index, N1x, notes table, harmony, engrave, render, export, no music21; `engine:152`); music21 for `part_writing.check` (`engine:153`, 114 MB, `engine:148`) is a required dependency of Reflets (open question 7), so `check` always works; the AnalysisGNN environment is a separate optional download (`engine:22`, `notes:67`).
- Settings: `REFLETS_PORT` (default 8731), `REFLETS_TMP`, `REFLETS_LOG`.
- Licence: plugin and server MIT; the plugin is written from scratch against the public API and does not copy the GPL-3.0 `dev_test_websocket` sample (`hosts:57`, `hosts:58`, `hosts:63`).

39. **Meter changes in ideas.** Decided 2026-10-20: a `ts=` that keeps the bar's length (4/4 to 12/8 or 2/2) moves nothing and is always written; one that changes it only when every bar from there to the next meter change or the end is empty, since MuseScore re-bars the music after it. 40. **Key changes in ideas.** Decided 2026-10-20: `ks=` (the concert key) changes every staff from that bar to the next key change; since MuseScore's key change command, which works out a transposing staff's written key, is not open to plugins, the server computes each staff's written key from its transposition and adds one key signature per staff, to be tested live on a score with a B-flat clarinet.
